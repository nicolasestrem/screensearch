# ScreenSearch V2c: 0.4.5 Roadmap: Work Intelligence + Full Refont

> **Repo destination:** `docs/0.4.5.md` (sibling of `docs/0.4.0.md`).
> **Arc name:** **P9: Work intelligence + design system v2.**
> **Base:** v0.4.2 (schema 13) plus the unreleased `main` increments (#145 llama.cpp bootstrap
> recovery, setup visibility `03 §7g`). Those ship in the first wave tag.
> **Operating model:** every phase follows `specs/04_CLAUDE_CODE_BUILD_PROMPT.md` (mandatory reading
> order, stop-at-ambiguity, verbatim verification, build-loop outputs `05`–`08`). P1 extends `04`
> to cover this arc. The **specs are the contract**; this roadmap is context once P1 lands.
> **Execution model (maintainer's):** P1 alone, then three waves of three phases. While wave N
> executes, wave N-1 is in its debug window. Each wave closes with a gate and a tag:
> **v0.4.3** (wave A), **v0.4.4** (wave B), **v0.4.5** (wave C).

---

## 1. Why this arc exists

Two problems, one arc.

**1. ScreenSearch records my work but does not understand it.** The data is there: frames,
content text, sessions with tool/host/context keys and lazy summaries, marks, daily reports,
weekly syntheses, one project note. What is missing is the layer that turns it into answers about
*my work*:

- **Insights is counts, not insights.** `InsightsSummary` is totals, capture density, top apps and
  an activity breakdown. Nothing in it says what I worked on, what is still open, or what connects.
- **Ask is frame-level.** It retrieves frames and answers. It cannot resolve "the Dockhouse
  project", cannot reason over "last week, before the release", and cannot hop from a session to
  the three earlier sessions on the same thing.
- **Nothing links across days.** A repo, a document, an error string, a ticket seen on Monday and
  again on Thursday are two unrelated piles of frames.

The arc adds a **work graph** (entities extracted from what I actually looked at, linked to
sessions, clustered into threads), a **session-aware Ask** that plans over time and entities, and
an **insights engine** whose every observation is typed and cited. Same rules as F3: uncited
claims are defects, not style.

**2. The interface is not good enough, and Settings is the worst of it.** `routes/Settings.tsx`
is 1,362 lines: fourteen stacked panels in one scroll (Capture, Hotkeys, Privacy, Models, Storage,
Data export, then Capture tuning, Text source / UIA, Enrichment & scheduling, Sessions,
Performance throttle, Text filtering, Reports & retrieval, Inference engine), around sixty keys,
many of them engine internals that no person should have to reason about. 0.3.2 was deliberately
"structural only, no visual redesign" (D12) and 0.4.0 parked the token-level refresh as #104
"its own conversation amending `UI_REFERENCE §1` first". **This is that conversation.** Colours,
type, spacing, radii, buttons, fields, every primitive, every screen: all of it is redesigned on a
new token architecture.

**What makes this arc possible: there is exactly one user.** The maintainer is the only person
running this software. P1 records that as a product fact and removes the obligations that existed
for other users (forward-only migrations with populated-DB tests, settings-load tolerance for
retired keys, removal call-outs in release notes, multi-environment pilot validation). That cuts
a large share of the cost of an arc this size.

### Wave A: foundations (P2 · P3 · P4), tag v0.4.3 at Gate A

#### P2: Design system v2 (UI foundation)

**Goal:** a new visual language, delivered as tokens and primitives, before any screen is touched.

1. **Direction checkpoint (stop point, maintainer decides).** Build a dev-only `/kitchen` route
   that renders **three complete directions** on the same content: a real Settings page, a search
   result list, a session card, an answer with citations, a form with every control state, both
   themes where the direction has two. The maintainer picks one (or a merge) and the choice is
   written into `UI_REFERENCE §1`. Nothing below starts before the pick.
2. **Token architecture, three layers** in `ui/src/styles/tokens.css`:
   *primitive* (raw scales: colour ramps, type scale, space scale, radii, shadows, durations) →
   *semantic* (`--surface-raised`, `--text-secondary`, `--border-subtle`, `--action-primary-bg`,
   `--focus-ring`…) → *component* (only where a component needs its own knob).
   Components may reference **semantic and component tokens only**. Themes are semantic-layer
   swaps (`[data-theme]`).
3. **Typography:** bundled, OFL-licensed variable fonts shipped as local files in the app (no
   network, keeps the offline/privacy rule that motivated the old "native fonts only" stance).
   One text family, one mono family; display treatment comes from weight/size, not a third face.
4. **Spacing and layout:** a 4-based scale with named steps, a density token
   (`comfortable` / `compact`), container widths, a 12-column content grid for wide screens.
5. **Primitives rebuilt from zero:** Button (primary / secondary / ghost / danger × sm / md, icon
   and loading states), IconButton, Field, TextInput, Textarea, Select, Combobox, Toggle,
   Checkbox, Radio group, Segmented control, Slider with numeric input, Chip/Tag, Badge, Tooltip,
   Popover, Dialog, Sheet, Toast, Tabs, Panel/Card, List row, Table, Skeleton, EmptyState,
   ErrorState, Kbd, Divider. Every primitive: all interaction states, keyboard behaviour, focus
   ring, reduced motion, WCAG-AA contrast in every theme.
6. **Icons:** one consistent icon set (local SVGs, single stroke width), replacing the
   hand-maintained `components/icons.tsx`.
7. **Compat shim:** the old token names are aliased onto v2 semantic tokens in one file
   (`tokens.compat.css`) so unconverted screens keep rendering. P10 deletes it.

**Acceptance:** `/kitchen` renders every primitive in every state and theme; an automated
contrast check over the semantic pairs passes AA; lint rule (or a test) fails on raw hex, px
font sizes or non-token spacing in `ui/src/components/primitives`; existing screens still render
through the shim (screenshots attached to the PR); full verification suite green.

#### P3: Baseline schema v14 + settings v2 model (backend)

**Goal:** one clean schema and one honest settings model, both cut for a single user.

- **Baseline schema (D2):** `crates/store` loses the migration chain; `schema.rs` holds the v14
  DDL from `03 §4` verbatim. On open, a DB at v14 opens; anything else refuses with a clear
  message pointing at the rebuild tool.
- **One-shot rebuild tool (D3):** a dev binary (`ssv2c-rebuild`, in `crates/harness` or a sibling
  dev crate, not shipped) that reads the old v13 DB **read-only** and writes a fresh v14 DB:
  frames, images (by path), content/raw text, text embeddings, sessions, session artifacts,
  marks, report runs and saved reports, API history/allocator metadata, read tokens. Derived data
  that v14 reshapes is dropped and re-derived. The old file is never modified; it is renamed to
  `*.v13.bak` only after the maintainer confirms the new one opens.
- **Settings v2 (D6):** implement the `03 §8` key table: delete retired keys from
  `crates/traits` and every consumer; move *file-only* keys to a documented `advanced.toml`
  section read at startup; regenerate bindings. **No load tolerance** for retired keys: a
  settings file with unknown keys is rewritten once with them removed.
- New tables are created empty; nothing writes them yet (P5/P6/P8 do).

**Acceptance:** rebuild tool run against a copy of the maintainer's real DB, with row counts per
table before/after pasted verbatim and a spot check of 20 random frames opening in Moment; app
boots on v14; settings round-trip test over the v2 key set; `cargo test` green; bindings diff
committed.

#### P4: Automatic intelligence evaluation (dev-only, read-only, zero maintainer input)

**Goal:** measure Ask and the work graph before changing them, without asking the maintainer to
write questions or label anything. **No hand-written golden set, no manual labelling** (D17).

- Extend `crates/harness` (dev-only, never shipped) with an **eval runner** over the real DB.
- **Self-generated questions from facts the DB already knows.** The runner derives question and
  answer pairs mechanically from ground truth that exists in the data:
  - *last-seen:* "When did I last have `<file / document / domain>` open?" → answer from frame
    timestamps.
  - *involvement:* "Which sessions involved `<repo / domain>`?" → answer from window titles, URLs
    and paths matching that string.
  - *sequence:* "What was I doing before session `<Z>`?" → answer from session order.
  - *window recall:* "What did I work on `<date, morning>`?" → answer from the sessions in that
    window.
  - *seen-again:* "Where else did this text appear?" → answer from exact FTS matches of a sampled
    distinctive string.
  Several hundred pairs per run, regenerated each run, so they never go stale.
- **Entity check without labels:** entities that are unambiguous by construction (exact repo
  paths, full URLs, `#123` refs) are the reference; the engine is scored on recovering them and on
  not inventing ones that are absent from the text.
- **Metrics (all automatic):** retrieval recall@10, citation validity (every cited id exists and
  is in window), answer contains the known fact (string / timestamp / id match), entity recovery,
  latency p50/p95.
- Run it on **current** Ask and record the baseline in `05`/`06`. These numbers become P5/P6
  acceptance thresholds (frozen at Gate A).

**Acceptance:** baseline report pasted verbatim; the generators are deterministic for a given DB
and seed (test); the harness opens the DB read-only (test asserts it); zero maintainer input
required to run it.

### Wave B: engines + shell (P5 · P6 · P7), tag v0.4.4 at Gate B

#### P5: Work graph engine (Rust)

- New crate `crates/graph` (pure logic, depends on `traits` only) + store queries + kernel jobs.
- **Extraction (heuristic first):** from window titles, URLs (domain + path shape), file paths,
  repo names, terminal cwd/prompts, IDE titles, document titles, issue/PR refs (`#123`,
  `ABC-123`), using the existing `crates/sessions` tool recognition as input. Each hit carries a
  source and a confidence.
- **Normalization (LLM, idle/on demand):** an optional pass over session summaries that proposes
  canonical names and aliases (`screensearch-v2c` = `ScreenSearch` = `screensearch.app`). Proposals
  land in `entity_aliases` with provenance; heuristic entities never depend on the model.
- **Threads:** sessions sharing strong entities within a decaying time window cluster into
  threads; `thread_overrides` (rename / merge / split, written by P9's UI) always win over the
  clusterer. Clustering is deterministic for a given input and override set.
- **Backfill:** a resumable job over the full rebuilt history; progress visible through the
  existing setup/job status surfaces.

**Acceptance:** entity recovery on the P4 automatic set at or above the thresholds frozen at
Gate A; backfill over the real DB completes with counts pasted; determinism test (same input →
same threads); override precedence tests.

#### P6: Ask v2 (retrieval + planning + multi-turn)

- **Session vectors:** embed session titles + summaries into `session_vectors` (fastembed, same
  model as text) as a new job kind; backfill.
- **Planner:** parse time intent ("last week", "before the release", "this morning") into
  windows; resolve entity mentions against `entities`/`entity_aliases` when present (falls back to
  text when P5 data is absent, so P6 does not block on P5).
- **Retrieval stages:** threads → sessions (hybrid: FTS + session vectors) → frames inside the
  winning sessions (existing hybrid search) → context assembly with a token budget.
- **Answers** cite sessions *and* frames; the existing `/v1/ask` SSE stream gains session
  citations (wire change allowed, D12).
- **Multi-turn:** `ask_threads` / `ask_turns` persist conversations; follow-ups reuse the
  previous turn's resolved window and entities.

**Acceptance:** on the P4 automatic set, recall@10 and known-fact answer rate beat the baseline by the
margins frozen at Gate A; citation validity 100%; p95 latency within the budget frozen at Gate A;
full suite green.

#### P7: App shell, navigation and Settings v2 (UI, on P2 primitives)

- **Shell:** NavRail, StatusRail, CommandPalette, QuickActions, toasts, readiness/setup banners
  rebuilt on v2. New IA (D7) wired with route skeletons for the screens P9/P10 fill.
- **Settings v2:** a dedicated layout: category sidebar (General, Capture, Privacy,
  Intelligence, Models, Data, Integrations, Advanced), **search across all settings** (#103),
  one row pattern everywhere (label, one-line plain-language effect, control, "changed" marker
  with reset-to-default), **autosave per field with undo toast** (D9), destructive actions behind
  a confirm dialog, live status inline where a setting has a runtime effect (hotkey registered,
  API listening on, model loaded). API/token/Telegram/Obsidian controls move to Integrations;
  `advanced.toml` keys are shown read-only under Advanced with the file path.
- Settings.tsx is replaced by a `routes/settings/` folder, one file per category; no file over
  ~300 lines.

**Acceptance:** every UI key from `03 §8` reachable and round-trips; search finds every setting by
label and by key; keyboard-only pass through all categories; state matrix (loading / empty /
error / partial / populated) per category; screenshots in both themes; external-agent read
credential UI verified natively (closes that `05` gate).

### Wave C: intelligence surfaces + full refont (P8 · P9 · P10), tag v0.4.5 at Gate C

#### P8: Insights + connections engine, agent surface (backend)

- **Insight types (D10):** *thread activity* (time and sessions per thread over a window, last
  touched), *open loops* (unresolved marks, open questions from weekly syntheses, threads
  abandoned mid-way), *recurrence* (the same error string / document / ticket seen again after a
  gap, via FTS near-duplicate + entity match), *semantic neighbours* (sessions similar to this one
  on other days, via session vectors), *resumption* (a thread picked up after N days, with what it
  was last doing).
- Each insight is a row in `insights` with typed payload and `insight_evidence` ids. Optional
  LLM phrasing on top; the typed payload is the truth and renders without the model.
- **Generation:** on demand and on idle (D11); never notifies (D13).
- **Feeding memory:** weekly synthesis and daily reports may cite insights (additive; report
  formats otherwise unchanged).
- **Agent surface:** read routes `GET /v1/threads`, `/v1/threads/{id}`, `/v1/entities`,
  `/v1/insights`; MCP tools `list_threads`, `get_thread`, `find_connections`, `list_insights`;
  `docs/API.md` and `docs/MCP.md` updated; the maintainer's own consumers (Hermes / second-brain
  pipeline) updated in the same window (D12).

**Acceptance:** each insight type has a fixture test and a real-DB sample pasted; no insight row
without evidence (constraint + test); API routes covered by integration tests behind read
credentials; MCP round trip against the live app.

#### P9: Intelligence UI (new screens)

- **Work** route: threads list (sortable by last touched / time spent), thread page (timeline of
  its sessions, entities, open loops, connected threads, Ask scoped to the thread), rename /
  merge / split writing `thread_overrides`.
- **Insights** route rewritten: cited insight cards grouped by type, window picker, each card
  opens its evidence.
- **Ask v2 UI:** conversation view with persisted threads, session + frame citations, scope chips
  (time window, thread, entity) the user can edit.
- **Connection components** (`ConnectionsPanel`, `EntityChips`) built here for P10 to place in
  Session and Moment.

**Acceptance:** full state matrix per screen; keyboard paths; every rendered claim links to
evidence; screenshots both themes; a 10-question spot check from the P4 automatic set asked through the UI, results recorded.

#### P10: Recall surfaces refont + shim removal

- Deck, Search/Recall, Timeline (Scanline or its v2 successor per the chosen direction), Session,
  Moment, Flow overlay, Reports/Memory panels, Promotion dialog: rebuilt on v2, placing P9's
  connection components in Session and Moment.
- **Delete `tokens.compat.css`** and every legacy token; the lint rule from P2 extends to all of
  `ui/src`.
- Remove dead components left behind by the redesign.

**Acceptance:** zero legacy tokens (grep pasted); lint gate across `ui/src`; per-screen state
matrix; performance budgets from `UI_REFERENCE §8` re-measured and pasted; overlay still covered
by the self-exclude capture gate (test).

## 4. Running three-and-three: the rules that make it safe

1. **"Executing" ends at merge; "debugging" is dogfooding the merged build.** A phase is done when
   its PR merges with acceptance evidence. The debug window is the maintainer driving that build
   daily. Fixes go to short `fix/` branches against `main`, merged the same day.
2. **Next wave starts when all three phases of the current wave are merged**, not when its debug
   window ends.
3. **File ownership per phase.** Each phase's PR1-style kickoff lists the paths it owns. Two
   phases in the same wave never edit the same file. Planned ownership:
   - Wave A: P2 `ui/src/styles`, `ui/tailwind.config.*`, `ui/src/components/primitives`,
     `ui/src/routes/Kitchen*` · P3 `crates/store`, `crates/traits` settings, settings consumers,
     `ui/src/bindings` · P4 `crates/harness`.
   - Wave B: P5 `crates/graph`, `crates/sessions` (read-side only), graph jobs in `crates/kernel` ·
     P6 `crates/inference` ask path, ask pipeline in `crates/kernel`, store retrieval queries ·
     P7 `ui/src/components/shell`, `ui/src/routes/settings/`, `ui/src/app`.
     *Overlap to manage:* P5 and P6 both add kernel jobs: each in its own module file, one shared
     edit to the job-kind registry made by P5 first.
   - Wave C: P8 `crates/api`, `crates/mcp`, insights in `crates/kernel`/`crates/store` · P9 new
     routes `Work`, `Insights`, `Ask`, `components/intelligence/` · P10 every existing route and
     `components/domain`.
4. **Daily rebase.** Executing branches rebase on `main` every day so debug-window fixes reach
   them immediately.
5. **Pull the brake on design-level bugs.** If a debug window finds a flaw in a foundation
   (P2 tokens, P3 schema, P4 metrics) rather than a bug, the dependent executing phase pauses until
   the fix merges. Tolerating it for a week costs more than the pause.
6. **One schema owner.** Only P3 touches the DDL. Any later phase that needs a schema change stops
   and amends `03 §4` first; with D2 that is a cheap baseline edit plus a rebuild, but it is still
   a contract change, not a silent one.

## 5. Gates

Each gate closes a wave's debug window and tags a release through the existing signed updater.

- **Gate A → v0.4.3:** design direction recorded; rebuild tool used for real; app runs on v14 for
  at least 3 working days without blocker; P4 baseline numbers frozen as P6/P5 thresholds;
  F3 native interactive acceptance performed (closes that `05` gate). Ships the pending `main`
  increments (#145, setup visibility).
- **Gate B → v0.4.4:** P5/P6 thresholds met on the P4 automatic set (report pasted); Settings v2 in daily
  use; external-agent Settings UI verified.
- **Gate C → v0.4.5:** full `04` audit; every `UI_REFERENCE §10` criterion on every screen;
  P4 automatic set rerun end to end; separate-machine API check; `05`–`08` swept and
  archived per `04 §7`; CHANGELOG and release notes.

## 7. Risks

| Risk | Mitigation |
|---|---|
| Parallel UI phases collide (the refont touches every file) | File ownership per phase (§4.3); at most one "broad" UI phase per wave; compat shim keeps unconverted screens alive until P10. |
| Debugging wave N-1 while building on it | Daily rebase; same-day fix merges; brake rule for foundation-level flaws (§4.5). |
