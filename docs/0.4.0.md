# ScreenSearch V2c — 0.4.0 Roadmap: The Sessions Arc

> **Repo destination:** `docs/0.4.0.md` (sibling of `docs/0.3.2.md`).
> **Arc name:** **P8 — Sessions (frames → sessions reframe).**
> **Operating model:** identical to the 0.2.x–0.3.x arcs — every PR follows
> `specs/04_CLAUDE_CODE_BUILD_PROMPT.md` (mandatory reading order, stop-at-ambiguity,
> verbatim verification, build-loop outputs `05`–`08`), and **recycles `specs/04` as the
> per-PR operating prompt**. PR1 extends `specs/04` to cover this arc.
> **Arc constraints (hard):** exactly **one** schema migration (PR3, schema **10 → 11**,

> **Delivery:** v0.4.0 is the **first auto-delivered release** — the 0.3.2/0.3.3
> updater population receives it automatically (D16 gates the tag on a live
> update-path test).

## 1. Why this arc exists

Everything shipped so far treats the **frame** as the unit of recall. That was the right
foundation, but it is not how the maintainer — or an AI agent — actually thinks about
the day. Nobody asks "show me frame 48 213"; they ask "what happened in **that
meeting**", "what did **that Claude Code run** change", "what was I doing **before
lunch**". The strategic direction (ambient memory for AI coding agents via the MCP
layer, plus personal recall) needs both askable units to be **sessions**.

Two issues have been deliberately parked waiting for this arc, on the explicit rationale
that building them on frames would be throwaway work:

- **#54** (closed 0.3.1, D7 → gap `07` #98): app-name / window-title keyword
  intelligence — exactly the `app_hint` input the segmentation heuristic needs.
- **#88** (deferred 0.3.2, D11 → gap `07` #102): recognizing Codex / Claude Code /
  terminal-vs-desktop is the same recognition input; distinguishing **user input from
  agent output** is a *sessions-schema* concern, meaningless before session objects
  exist. #88 is the **anchor issue** of this arc and closes with it.

The app already computes a proto-session every day: `where_was_i`'s "last sustained
context" (a run of frames sharing a context key for ≥ `resume.min_dwell_secs`). Sessions
generalize that heuristic from "the one run behind me" to "every run, persisted, with a
stable identity" — then make those objects visible in the UI and queryable over the
API/MCP surface, which is the arc's strategic payoff: *an agent can ask what happened in
the user's last session with a given tool.*

The hard sequencing constraint recorded since 0.3.1 — **auto-update must land before
0.4.0 ships** — was satisfied by 0.3.2. Nothing gates this arc anymore.

One reality check that shapes the risk posture throughout: as of this writing there is
**one known production install** (the maintainer's). The arc's single migration must be
engineered to the usual standard (D4), but rollback theater is not warranted; a dated
backup of the one live DB (D5) — which is also the arc's ground-truth dataset — is the
proportionate safety net. See D15 for how the "is anyone else out there?" question gets
answered without ever adding telemetry.

### PR2 — Ground truth + segmentation validation harness (read-only; dedicated kickoff)

The arc's mandatory evidence phase, in the spirit of 0.3.1 PR2's profiling phase: **no
segmenter ships untested against the real data.** The maintainer's live DB — frames,
`app_hint` / `window_title` / `browser_url` context, and the accumulated mark history —
is the ground-truth dataset (the standing plan has said so since 0.3.2 §6). This PR
touches **no schema and no shipped code paths**; its deliverable is a dev-only harness
plus recorded evidence.

**Phase A — ground truth assembly (maintainer-in-the-loop, bounded):**
1. Read-only export of frame metadata + marks from the live DB for a representative
   sample — target **5–10 days** chosen to include: at least one meeting-heavy day, at
   least one Claude Code day, at least one Codex day, one browser-AI day, one mixed/
   fragmented day.
2. The maintainer hand-labels session boundaries and tool identities for those days
   (a lightweight labeling format the harness defines; the marks are anchors, not the
   full labels). Keep the labeling burden under an evening's work — if it balloons,
   shrink the sample, don't skip the phase.

**Phase B — the harness:**
3. A pure candidate segmenter (a function over ordered frame-metadata sequences — the
   `where_was_i` context key generalized: `app_hint` ⊕ browser domain ⊕ taxonomy tool
   identity, with gap/close parameters) replayed over the exported days.
4. Scoring: boundary precision/recall against the hand labels (with a ± tolerance
   window), plus tool-recognition accuracy on the labeled AI sessions. Parameters and
   taxonomy patterns tuned **here**, on evidence, not in PR4 on vibes.

**Phase C — thresholds:**
5. Propose the D9 acceptance thresholds from what the data actually supports; the
   maintainer approves them; record numbers + parameterization in `05`/`06` — they
   become PR4's merge gate.

**Stop condition (hard):** if no reasonable parameterization reaches credible boundary
agreement on the real data, **stop and report** — the arc redesigns (different signals,
different session definition) *before* PR3 freezes a schema around a heuristic that
doesn't work. Do not proceed to PR3 with an unvalidated design.

**PR2 acceptance:** the harness runs end-to-end on the exported sample; scores +
chosen parameters + proposed thresholds recorded in `05`/`06`; the labeled dataset is
kept **local-only** (it is personal screen history — git-ignored, never committed).

### PR3 — Sessions schema + the migration (schema 10 → 11; dedicated kickoff)

The arc's **only** schema change (D4). Informed by PR2's findings (e.g., whether
`context_key` needs more structure than the sketch below).

Proposal-level DDL — PR1 normalizes the final form into `03 §4`:

```sql
CREATE TABLE sessions (
  id            INTEGER PRIMARY KEY,
  started_at    INTEGER NOT NULL,                 -- unix ms
  ended_at      INTEGER,                          -- NULL = open
  kind          TEXT NOT NULL CHECK (kind IN ('focus','meeting','ai','other')),
  tool          TEXT,                             -- taxonomy id ('claude-code','codex',…); NULL unless kind='ai'
  host          TEXT CHECK (host IN ('terminal','desktop','browser','ide')),
  context_key   TEXT NOT NULL,                    -- the segmenter's key (03 contract)
  title         TEXT,                             -- lazily generated, cached (D3)
  summary       TEXT,                             -- lazily generated, cached (D3)
  summary_model TEXT,
  confidence    REAL NOT NULL,
  frozen        INTEGER NOT NULL DEFAULT 0 CHECK (frozen IN (0,1)),  -- D2
  created_at    INTEGER NOT NULL DEFAULT (unixepoch()*1000),
  updated_at    INTEGER NOT NULL DEFAULT (unixepoch()*1000)
);
CREATE INDEX idx_sessions_time ON sessions(started_at, ended_at);

ALTER TABLE frames ADD COLUMN session_id INTEGER REFERENCES sessions(id) ON DELETE SET NULL;
CREATE INDEX idx_frames_session ON frames(session_id);

-- The artifact extension point (D8). 'exchange' is used this arc; 'transcript' is
-- reserved for the audio arc; 'note' reserved for future annotation.
CREATE TABLE session_artifacts (
  id         INTEGER PRIMARY KEY,
  session_id INTEGER NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  kind       TEXT NOT NULL CHECK (kind IN ('exchange','transcript','note')),
  role       TEXT CHECK (role IN ('user','agent')),
  frame_id   INTEGER REFERENCES frames(id) ON DELETE SET NULL,
  content    TEXT NOT NULL,
  created_at INTEGER NOT NULL DEFAULT (unixepoch()*1000)
);
CREATE INDEX idx_artifacts_session ON session_artifacts(session_id, created_at);
```

Mechanics:
- Forward-only, bumps `schema_version` by **exactly one** (10 → 11), next integer
  confirmed against `crates/store/src/schema.rs::LATEST_SCHEMA_VERSION`, never
  hardcoded (the D15-of-0.3.0 rule, restated here as D4).
- **Populated-DB migration test** using a schema-10 fixture with real-shaped data
  (frames with `app_hint`/`window_title`/`browser_url`, marks, embeddings, jobs) — the
  0.2.1 `frames`-rebuild test is the pattern. Fresh-DB and migrated-DB schemas must
  agree.
- **Backup gate (D5):** before this branch's build is ever pointed at the live DB, a
  dated copy of `screensearch.db` exists outside the app data dir. Release-blocker-class
  manual step, recorded in `07`'s manual-steps section by PR1 — the live DB is also the
  PR2 ground-truth dataset; losing it loses the arc's evidence.
- No backfill obligation: pre-existing frames get sessions assigned by PR4's segmenter
  running over history as a background job, not by the migration itself. The migration
  creates structure only and stays fast.

**PR3 acceptance:** migration test green on the populated fixture; fresh/migrated
schema parity shown; every frame-level feature (search, Ask, reports, marks, overlay,
where-was-i) demonstrably unchanged on the fixture (D10); backup-gate step documented.

### PR4 — The segmentation engine + recognition (Rust)

The heuristic that PR2 validated, productionized:

- **A pure segmentation core** behind a trait (proposed home: a new small `sessions`
  crate, or `kernel` if the crate tax isn't worth it — implementer's call, recorded in
  `08`), scheduled by `kernel` as an incremental background pass: assign new frames to
  open sessions by context-key continuity; close a session when the gap or context
  switch exceeds the close rule; **freeze** (D2) sessions once closed and outside the
  segmenter's lookback window. A one-shot historical pass over pre-0.4.0 frames runs as
  a normal background job (resumable, low priority — never competes with capture).
- **The taxonomy file** (D6/D7): versioned data file in the repo, seeded per D7, loaded
  at startup. Recognition emits `kind` / `tool` / `host` on sessions. No model calls
  anywhere in segmentation (D3).
- **Exchange extraction (D8, best-effort):** for recognized AI sessions, tool-specific
  markers over `content_text` (never raw full-screen text — the 0.2.x rule holds)
  extract user-vs-agent exchanges into `session_artifacts`. Explicitly best-effort:
  when markers don't match, the session simply has no exchanges — never invented roles.
- **Lazy intelligence (D3):** session `title`/`summary` generate on demand and cache on
  the row; the **session recap reuses the existing coverage-first report engine**
  scoped to the session's time range and frames — no new summarization machinery, ctx
  stays pinned at 8192.
- **New settings keys** (the arc's only new settings surface, both clamped, homes per
  the two-tier IA): `sessions.min_len_secs` (default 120 — mirrors
  `resume.min_dwell_secs`) and `sessions.gap_close_secs` (default 120 after the 11-day
  production-data sweep; usage review 2026-08-01 §6.7).

**PR4 acceptance (the D9 gate):** the shipped segmenter meets the PR2-recorded
thresholds when re-run through the harness; recognition demonstrated live on a real
Claude Code session, a Codex session, a browser-AI session, and a meeting-titled
window; the historical pass completes on the live DB without disturbing capture;
exchange extraction shown on a real AI session (qualitative, maintainer-judged);
where-was-i and all frame-level features unchanged.

## 4. Pre-answered product decisions (D1–D16)

Settled here so the agent only stops on genuinely new ambiguity.

- **D1 — Sessions are derived-but-persisted; frames stay the source of truth.**
  Deleting or regenerating session rows never touches frames, text, embeddings, or
  marks. A wiped `sessions` table is fully recomputable from frames.
- **D2 — Stable IDs via the freeze rule.** A session closes by the gap/close rules;
  once closed and older than the segmenter's lookback window, its `id` and boundaries
  **freeze** (immutable). Resegmentation only ever touches unfrozen (open/recent)
  sessions. This is what makes session IDs safe to hand to MCP consumers.
- **D3 — Lazy intelligence.** Session creation is pure heuristic — zero model calls.
  Titles, summaries, and recaps are generated on demand and cached; the recap **is**
  the existing report engine scoped to the session. Context stays pinned at 8192.
- **D4 — One migration, PR3 only, schema 10 → 11.** D15-of-0.3.0 mechanics apply
  (bump by exactly one, confirmed against `schema.rs`, populated-DB migration test).
  If any other PR appears to need schema, that PR is wrong — stop and report.
- **D5 — Pre-migration backup is a release-blocker-class manual step.** A dated copy
  of the live `screensearch.db` exists before any 0.4.0 build touches it. The live DB
  is simultaneously the only production install and the ground-truth dataset.
- **D6 — The taxonomy is a versioned data file, not schema and not settings.** It
  lives in the repo, compiles/ships with the app, and adding a tool = editing the
  file. A user-editable override file is **deferred** (record in `07`).
- **D7 — Recognition dimensions and seed set.** Two dimensions: tool identity ×
  host (`terminal` / `desktop` / `browser` / `ide`). Seed tools: `claude-code`,
  `codex`, `claude-desktop`, `cursor`, `vscode`, `browser-ai` (claude.ai,
  chatgpt.com, gemini.google.com domains via `browser_url`); seed meetings: Zoom,
  Teams, Meet, Webex, Discord (app hints + window-title patterns). Patterns are tuned
  in PR2 against real captures, not guessed.
- **D8 — Roles live on session artifacts, not on spans.** User-vs-agent separation
  lands as `session_artifacts` rows (`kind='exchange'`, `role IN ('user','agent')`),
  extracted best-effort from `content_text` via tool-specific markers. The span schema
  and `TextRole` (chrome/content) are untouched — the two classification axes stay
  separate. `'transcript'` is reserved for the audio arc: the extension point, made
  concrete this arc instead of staying hypothetical.
- **D9 — The validation gate is binding.** PR4 merges only if it meets the thresholds
  PR2 established on the real-DB harness (numbers proposed by PR2, approved by the
  maintainer, recorded in `05`/`06`). A miss is a stop-and-report, not a
  tune-until-green.
- **D10 — Sessions are additive.** Zero behavior change to frame-level capture,
  search, Ask, reports, marks, overlay, or where-was-i. Sessions never gate capture;
  a segmenter failure degrades to "no sessions", never to lost frames.
- **D11 — Pull-based and non-shaming, reaffirmed and binding.** No session
  notifications, no "you spent 4 hours in X" nudges, no streaks, no scores. Session
  surfaces are truthful, on-demand, and neutral in tone — the D6-of-0.3.1 /
  D4-of-0.3.2 lineage continues.
- **D12 — The API/MCP surface is read-only.** `GET /v1/sessions`,
  `GET /v1/sessions/{id}`, and a `session_id` scope on `/v1/ask`; MCP gains
  `list_sessions` / `get_session` / `ask_session`. No new write scopes; the MCP server
  remains a stdio wrapper over the HTTP API (0.3.0 D13).
- **D13 — No new NavRail route this arc.** Sessions surface inside Timeline (bands +
  drill-in), Moment, and the Deck card. A dedicated Sessions route is a 0.4.x
  conversation *after* live use shows it's needed — record the possibility in `07`.
- **D14 — Meetings are metadata-only.** `kind='meeting'` sessions carry no audio and
  no transcript in 0.4.0; the audio arc (0.4.1/0.5.0, EU/French consent UX and all)
  attaches transcripts as session artifacts later. Anything audio-shaped in this arc
  is a scope violation.
- **D15 — Usage awareness without telemetry.** The app never phones home beyond the
  existing updater manifest fetch — that is a permanent product commitment, restated
  in `02 §7`. The maintainer's "is anyone else using this?" question is answered by
  **passive repo-side signals**: GitHub release-asset `download_count` (the
  `latest.json` asset's count ≈ update checks across all updater-capable installs;
  the installer's count ≈ manual downloads), read against the maintainer's own known
  launch baseline, plus Insights → Traffic (unique cloners/visitors, 14-day window)
  and stars/issues. PR1 documents the reading procedure in `07`'s manual steps; an
  optional convenience script may live in `scripts/` (runs on the maintainer's
  machine, never in the app).
- **D16 — The first-auto-delivery gate.** v0.4.0 tags only after the live update path
  (0.3.2/0.3.3 install → auto-update → restart → 10→11 migration on first boot →
  sessions over pre-existing history) passes end-to-end on a real machine, with the
  D5 backup verified present beforehand.

## 5. Risks

| Risk | Note |
|---|---|
| The heuristic looks fine in design and fails on real days | PR2 exists precisely for this: evidence before schema, and the D9 gate is binding. The stop condition redesigns the arc *before* PR3 freezes anything. |
| The migration damages the only production DB | Blast radius is one machine, but that machine holds the ground-truth dataset. D5 backup + D4 populated-DB test; worst case is restore + re-run. Proportionate, not theatrical. |
| First auto-delivered release ships a broken update/migration path | D16 tests the exact live path before the tag. Worst case for the population (of ~1): a manual download — the pre-0.3.2 status quo. |
| Stable-ID promise vs. a better future heuristic | D2's freeze rule bounds the tension: history keeps its IDs; improvements apply going forward. A deliberate "resegment history" feature would be its own explicitly versioned arc item. |

## 7. Production-usage hardening (2026-08-01)

Three weeks of production capture exposed five scale- and lifecycle-dependent defects that the
pre-release fixtures could not reproduce. The full personal-data assessment remains git-ignored;
this tracked section records the resulting implementation contract and verification.

### 7.1 sqlite-vec KNN ceiling

sqlite-vec 0.1.9 rejects `k > 4096`. The bounded retrieval ladder previously escalated to 20,000,
so every date-filtered search at the API's default `limit=20` and 86 of 87 session-scoped asks
eventually returned HTTP 500 once the corpus exceeded 12,000 vectors.

- `SQLITE_VEC_MAX_K = 4096` is now the single external-engine constraint.
- Both the initial candidate pool and every geometric escalation step are clamped.
- The direct `nearest_text_frames` SQL boundary clamps independently as defense in depth.
- `COUNT_SCAN_CAP` remains linked to the KNN ceiling: sparse-window detection may give up sooner,
  but that only raises the target and can never discard an already-found match.
- A non-ignored regression seeds 4,200 production-width (768-dimensional) vectors and exercises
  date-ranged, five-frame session-scoped, and caller-controlled direct-KNN paths.

The failure mode is now fewer candidates at the engine ceiling, never an SQL error.

### 7.2 Capture is a backend lifecycle invariant

Capture start previously depended on the WebView reaching its mount command. Eight of 75 measured
launches never did, including one fully lost day, while the store, workers and local API continued
running without a visible failure.

- Tauri setup now starts capture after the kernel, managed state and tray are wired.
- Setup awaits capture start before it can finish and accept exit; immediate shutdown therefore
  stops an existing capture loop rather than allowing a deferred boot task to start one later.
- **Maintainer-approved policy override (2026-08-01):** backend boot-start supersedes the
  v0.1.0 gap #9 privacy-first opt-in rule. Stop remains an immediate session-local control; a
  relaunch starts capture again.
- The existing idempotent `Kernel::start_capture` remains the only start implementation, so the
  later frontend command is a harmless no-op.
- OCR/source failures warn and leave the app running instead of aborting setup.
- The tray is synchronized from the resulting readiness snapshot, closing the startup event race
  without polling; subsequent start/stop transitions still use the kernel event bus.

### 7.3 Session defaults retuned from production data

The 11-labelled-day sweep replaced the two-day defaults while preserving explicit user choices:

| Parameter | Previous | Production default | Rationale |
|---|---:|---:|---|
| `sessions.gap_close_secs` | 300 s | **120 s** | Better boundary F1, position F1 and tool accuracy |
| anchorless-focus density | 90 frames/h | **30 frames/h** | Higher F1 on the larger sample |
| anchorless-focus minimum | 600 s setting candidate | **600 s named constant** | Reclassified SENSITIVE → FLAT |
| stable-ID freeze lookback | 24 h | **6 h** | Zero boundary drift at 6/12/24/48 h over 25 days |

An existing exact legacy-default `sessions.gap_close_secs=300` is migrated once to 120. Fresh
installs likewise commit the default and migration marker together. These value-rewriting paths
commit atomically, so a failed migration leaves neither partial value nor marker. Existing custom
values are never rewritten when their marker is latched, allowing a concurrent explicit change to
win. Once latched, a later deliberate choice of 300 is preserved. Historical focus-length/density
rows are retired. The production harness defaults now match the shipped values.

### 7.4 Degenerate session-summary cache guard

One of four production summaries had cached the literal string `User`. Generation now validates
before persistence:

- whitespace-only values, summaries shorter than 32 Unicode scalar values, and standalone
  speaker tokens (`User`, `Assistant`, `System`, `Codex`, `ChatGPT`, `Human`, `AI`, with optional
  surrounding punctuation and case-insensitive matching) are rejected;
- a rejected generation retries exactly once;
- two rejections leave all cached title/summary/provenance fields `NULL`, return a terminal error
  so the Session UI exposes Retry rather than an indefinite generating state, and log only
  session id plus text length, never captured screen content;
- every in-app Session detail response redacts a pre-existing invalid cache; an
  `include_summary` request first clears it durably, then regenerates it when inference is
  available, so `User` is neither served while generation runs nor retained if inference is
  unavailable.

Model selection and exchange-role extraction remain separate concerns.

### 7.5 Query-boolean consistency

`GET /v1/search` now accepts `include_chrome=1`, `0`, `true`, or `false`
(case-insensitive). Absence remains `None` and falls back to
`text.include_chrome_default`; every other literal remains a JSON `400 bad_request`. The
downstream `Option<bool>` contract and search-ranking semantics are unchanged.
