## Contracts you must satisfy

**Kinds and payloads**

- `insights.kind` is the closed set of five: `thread_activity`, `open_loop`, `recurrence`,
  `semantic_neighbour`, `resumption`. A sixth kind is a schema change, i.e. a baseline edit plus a
  `schema_version` bump, and a stop (`03 §7j.1`, 0.4.5 D2).
- `insights.payload` is typed JSON and is the truth of the row: it must render completely without
  the model (`03 §7j.5`). Define one typed struct per kind in `crates/traits`, serialize it as the
  payload, and add one fixture test per kind that round-trips the struct and asserts the rendered
  fields (the shape itself is yours, per the P1 record).
- The payload shape is **additive**: never rename or repurpose a field that already shipped. If a
  later need demands a rename, that is a stop, not a refactor.
- `generator='heuristic'` means deterministically produced. `generator='llm_phrased'` means an LLM
  only restated a payload that already existed; phrasing is never the source of a claim, and a
  kind must produce its row with the model disabled (`03 §7j.5`, `§7h.2` for the same rule in the
  graph).
- `stale=1` marks a row whose window, entities or evidence changed since `generated_at`.
  Regeneration **replaces** the row (same kind, new payload and evidence) and never mutates a row
  in place under a reader; the old evidence rows disappear with it (`03 §7j.5`).
- Windows are unix ms and half-open, `[window_start, window_end)` (`03 §7j.5`, `§7i.1`).

**The evidence rule**

- Every `insights` row has at least one `insight_evidence` row. An insight without evidence is a
  defect, not a display problem (`03 §7j.2`).
- SQLite cannot express a deferred cross-table constraint, so enforce it exactly where it can be:
  the store's insert API writes the insight and its evidence **in one transaction** and returns an
  error when the evidence list is empty. No code path may create an unevidenced insight.
- A test asserts that rejection: insert with an empty evidence list, assert the error, assert no
  `insights` row was written.
- A sweep query, `SELECT id FROM insights WHERE id NOT IN (SELECT insight_id FROM
  insight_evidence)`, returns zero rows and runs as a harness invariant (`03 §7j.2`).
- `insight_evidence.kind` is one of `frame`, `session`, `thread`, `entity`, `mark`, `report`;
  `ref_id` is the referenced row's id and `ordinal` orders the evidence for display. `ordinal` is
  dense and starts at 0 or 1, one convention for the whole table, stated in `docs/API.md`.

**Generation**

- Generation runs **on demand** and **on idle** only, under the existing scheduler and pressure
  throttle (`03 §7j.3`, 0.4.5 D11). Never on the capture hot path; a throttled pass degrades to
  "insights are behind", never to a capture stall.
- A failing pass logs and degrades silently. A missing insight is not a UI error state, and stale
  insights are regenerated rather than repaired in place (`03 §7j.3`).
- Add exactly one job kind for generation and register it beside P5's four graph kinds and P6's
  vector kind, in the same registry. Adding a kind is not a schema change: `jobs.kind` is TEXT with
  no CHECK (gap `07` #82).
- Insights never notify. No notification, badge, streak, score, grade, daily prompt or ordering
  that implies a target (`03 §7j.4`, 0.4.5 D13). This is a hard product rule kept from 0.3.0 and
  0.4.0. If a request for one appears, it is out of contract.

**Reads never write**

- The four routes are GETs: none generates, regenerates or writes anything, and a read never starts
  inference. This is the rule the 0.4.0 session reads already follow (`03 §7c`).
- `GET /v1/threads` returns threads overlapping the requested window, in an order you state
  explicitly in `docs/API.md`.
- `GET /v1/threads/{id}` returns one thread with its sessions and its member entities.
- `GET /v1/entities` returns entities, filterable by kind and by name or alias substring.
- `GET /v1/insights` returns insights whose window overlaps the request, each with its evidence
  ids.
- Window and `limit` conventions follow `GET /v1/sessions`; an unknown query parameter or a
  malformed window is a typed error, never a silent default.

**Auth, MCP and docs**

- All four routes require `history.read`, are allowed for both credential classes, and add no new
  scope or class (`03 §7f.7`).
- The MCP wrapper gains exactly `list_threads`, `get_thread`, `find_connections`, `list_insights`
  over those routes. It stays a thin stdio HTTP client with no store access and no app coupling,
  and these four are read tools, so `--read-only` registers and dispatches them
  (`03 §7c`, `§7f.7`). Unknown tools are still rejected locally; the 401/403 semantics are
  unchanged.
- `docs/API.md` and `docs/MCP.md` are updated in this same phase with the routes, the parameters,
  the stated order, the evidence shape and the copy-paste client config (`03 §7c`, `§7f.7`,
  0.4.5 D12).
- D12 also requires the maintainer's own consumers (Hermes, the second-brain pipeline) updated in
  the same window. That work is outside this repository: publish the exact wire shapes in
  `docs/API.md` and record the handoff in `specs/07_KNOWN_GAPS.md` as maintainer-owned.

**Feeding memory**

- Weekly synthesis and daily reports may cite insights. The change is additive: report formats,
  the no-fabrication rules and the saved-file contracts stay as they are (`docs/0.4.5.md` P8,
  `03 §8b`, `§8c`, `§8e`). If citing an insight would need a report format change, stop.

**Code rules**

- No Python in the shipped runtime, no cloud inference, no new network destination (`04` §4).
- Thresholds are settings, never hardcoded (`03 §3b`, `§5`, `04` §4). If you need a numeric
  threshold that no setting covers, stop and record it: a new setting is a `03 §8` change.
- Typed wire definitions, no hand-rolled JSON strings where a struct fits (`03 §7f.6`).

## Stop conditions

Stop and ask, and record the item where indicated, when:

- a product decision is needed that the specs do not answer: log it in `specs/07_KNOWN_GAPS.md`;
- the specs contradict each other: log it in `specs/06_PATCH_PLAN.md`;
- the work needs a file outside the owned paths, including any edit to `crates/graph`,
  `crates/harness`, `crates/traits` settings types, `src-tauri` or the UI;
- a schema change is needed: stop and amend `03 §4` first, as a baseline edit plus a
  `schema_version` bump (0.4.5 D2, `docs/0.4.5.md` §4.6);
- any verification command stays red after a genuine fix attempt (`04` §6).

P8-specific:

- A kind cannot be produced from evidence that already exists in `frames`, `sessions`, `marks`,
  `report_runs`, `threads` or `entities`. Inventing a new evidence source is a product change.
- A payload cannot render completely without the model, or needs the model to be correct.
- A generation pass would need the capture hot path, or a scheduler path outside the existing
  scheduler and pressure throttle.
- A report format would have to change to cite an insight.
- A numeric threshold for recurrence, the resumption gap, or the neighbour similarity has no
  setting and no spec value. `03 §8` allows no unattributed config, so record it and stop.
- The evidence rule cannot be enforced in one transaction by the store API as it stands.
- `session_vectors` is empty or P6's job kind is not registered at your base, so
  `semantic_neighbour` cannot be produced. Do not build a second embedding path.

## Do not

- No stubs, no placeholder insight kinds, no mock evidence (`04` §4).
- No hardcoded expected values in tests, and no fixture passed off as a real-DB sample.
- No weakening of a test, a lint rule or an assertion to get green. If a rule is wrong, stop.
- No notification, badge, streak, score, grade or ordering that implies a target (0.4.5 D13).
- No write, generation or mutation on any GET route (`03 §7c`).
- No store access, no app coupling and no new scope class in the MCP wrapper (`03 §7f.7`).
- No commits to `main`, no push, no merge, and no commit or push at all until the maintainer
  validates the content and names the target repo `nicolasestrem/screensearch` (0.4.5 D18).
