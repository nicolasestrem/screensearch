Wave B of the 0.4.5 arc (P9: work intelligence + design system v2). Feeds **Gate B** and the
`v0.4.4` tag, and it is the phase that makes the P4 harness's entity metric measurable at all.

## Branch

`feat/0.4.5-p5-work-graph`, created from the `main` commit where **Gate A** has closed (the
`v0.4.3` tag commit), after every Wave A phase and its debug-window fixes are merged. Rebasing on
`main` daily is part of the phase (`docs/0.4.5.md` section 4, rule 4): debug-window fixes must reach
you the day they land.

No commit to `main`, no push, no merge, no review request until the maintainer has validated the
content and named the target repo (0.4.5 D18).

## Contracts you must satisfy

- **The crate is pure.** `crates/graph` depends on `traits` only (plus `anyhow`/`serde` if needed).
  No `rusqlite`, no `store`, no `kernel`, no `sessions`, no filesystem, no clock, no network. Every
  entry point takes plain input structs and returns plain output; time values are passed in as unix
  ms. The kernel owns I/O, the store owns SQL, the crate owns the rules. This is what makes the
  determinism test possible without a database.
- **Entity kinds are the closed six** (`03 §7h.1`): `repo`, `file`, `domain`, `document`, `ref`,
  `app`. No `topic` value, no people. `app` is **not** produced by heuristic extraction, because
  `§7h.2`'s source list contains no app-name source: `app` rows exist only when the normalization
  pass promotes a topic-shaped name.
- **Extraction is deterministic, model-free, and carries the rule's own confidence** (`§7h.2`).
  Implement exactly these rules over `frames.window_title`, `frames.browser_url`, `frames.app_hint`,
  the content text and the session's tool recognition (read-only input from `crates/sessions`):

  | Source | Rule | Kind | Confidence |
  |---|---|---|---|
  | browser URL | scheme plus host | `domain` | 0.95 |
  | browser URL | host only, no scheme | `domain` | 0.90 |
  | browser URL | path ending in a document extension | `document` | 0.85 |
  | browser URL | path of the form `/pull/<n>`, `/issues/<n>`, `/merge_requests/<n>` | `ref` | 0.95 |
  | any text | repository identity `<host>/<owner>/<repo>` | `repo` | 0.95 |
  | any text | absolute Windows path with a drive letter and an extension | `file` | 0.95 |
  | window title | document name ending in a document extension | `document` | 0.90 |
  | IDE title | leading file segment (`file - workspace - editor`) | `file` | 0.90 |
  | IDE title | workspace segment | `repo` | 0.80 |
  | terminal cwd or prompt | absolute directory path | `repo` | 0.80 |
  | any text | `ABC-123` style ticket key | `ref` | 0.85 |
  | any text | `#123` with an adjacent issue/PR/ticket word | `ref` | 0.85 |
  | any text | bare `#123` | `ref` | 0.60 |

  Confidence 0.60 is deliberately below the clustering threshold, so an unqualified number can
  exist as an entity but can never seed a thread. These are constants of the rule table, defined
  once in the crate, not scattered literals; a unit test asserts each rule's output and confidence.
  Record the table in `specs/05_BUILD_REVIEW.md` as a decision this phase takes, because `§7h.2`
  fixes the mechanism but not the numbers.
- **Dedup identity is `normalized_key`** (`§7h.2`, `§4`). Define it once and test it: lowercase;
  trim surrounding whitespace; backslashes to forward slashes; strip `http://`, `https://` and a
  leading `www.`; drop a URL fragment; drop a trailing slash; collapse repeated separators; keep the
  path for `file`, `document` and `repo`; keep the host and path for `domain` (no query string).
  `UNIQUE(kind, normalized_key)` then does the dedup, and `canonical_name` is the display form of
  the first hit that created the row.
- **Normalization is additive and optional** (`§7h.2`, second paragraph). The pass reads session
  summaries and proposes canonical names and aliases; it writes `entity_aliases` rows with
  `source='llm'` and its own confidence, and it **never** rewrites a heuristic entity's
  `normalized_key` or deletes a row. With no model loaded the pass is skipped and the graph is still
  complete and useful. There is no new settings key to enable it: the 0.4.5 settings surface is a
  closed set (0.4.5 D6, `03 §8`), so the pass runs opportunistically when an answer model is
  present and the machine is idle, and it logs when it is skipped.
- **Linking follows the interval** (`§7h.3`): a hit links to the session whose
  `[started_at, ended_at)` contains the hit's timestamp; an open session (`ended_at` NULL) is
  open-ended. One row per `(session_id, entity_id)`; `hit_count` counts distinct frames;
  `confidence` is the maximum of the contributing hits.
- **Clustering is deterministic and idempotent** (`§7h.4`). Two sessions are joined when they share
  at least one entity whose `session_entities.confidence` is at least 0.7 and the gap between their
  `last_seen_at` values is at most 30 days; the weight is 1.0 up to 7 days and decays linearly to 0
  at 30 days. Threads are the connected components of that relation. `threads.cluster_key` is the
  sorted list of the component's strong seed entity ids, serialized deterministically, and its
  `UNIQUE` constraint makes a re-run idempotent. `threads.title` is the dominant seed entity's
  `canonical_name`, where dominant means the highest summed edge weight (ties break to the lowest
  entity id); `session_count`, `first_seen_at` and `last_seen_at` derive from the members. A thread
  whose membership changes is rebuilt (delete and reinsert in one transaction), never hand-edited.
  `thread_sessions.session_id` is `UNIQUE`: a session belongs to at most one thread.
  Membership therefore depends on the 30-day boundary; the decay orders titles and weights, and
  this must be stated in the module documentation so nobody hunts for a hidden threshold.
- **Overrides are applied after clustering and always win** (`§7h.5`). Read `thread_overrides` in
  `(created_at, id)` order and apply: `rename` sets `threads.title` only; `merge` folds the source
  thread's `thread_sessions` rows into `target_thread_id` and deletes the emptied source; `split`
  moves the listed sessions into a new thread seeded by the override, whose `cluster_key` derives
  from the override rather than from the clusterer. `payload` is typed JSON validated by the
  `traits` types, and the table CHECK constrains which thread ids each kind may carry. Nothing in
  P5 inserts overrides: the UI writes them through the store API in P9.
- **Backfill is resumable without new state** (`§7h.6`, 0.4.5 D2 keeps the schema fixed and D6 keeps
  the settings surface closed). The queue itself is the checkpoint: `graph_backfill` enqueues a
  bounded batch of `graph_extract` jobs (each carrying a real `frame_id`, the column's actual
  meaning) for frames above the cursor `MAX(jobs.frame_id)` over that kind; the worker refills the
  next batch when the pending count drops below a low-water mark; the pass is complete when the
  cursor has reached `MAX(frames.id)`. Interrupting the app leaves pending and failed rows intact,
  and re-running continues from them. Every write is an upsert against the `UNIQUE` constraints, so
  a replayed chunk cannot duplicate rows. Batch sizes are kernel constants, never settings: a new
  key would violate the closed settings table (0.4.5 D6, `03 §8`).
  `graph_normalize` has no frame-scoped cursor (a session id may not be written into `frame_id`):
  it takes a bounded, most-recent-first batch of sessions with summaries each idle period, and the
  `UNIQUE(entity_id, alias)` constraint keeps replay idempotent. Record this in `05`.
- **Four job kinds, never on the capture hot path** (`§7h.7`, 0.4.5 D11): `graph_extract`,
  `graph_normalize`, `graph_cluster`, `graph_backfill`. They run on demand and on idle, under the
  existing scheduler and pressure throttle (`03 §5`); capture, OCR and storage never wait on one; a
  throttled graph job degrades to "the graph is behind" and to nothing else. Each job body lives in
  its own module file (`crates/kernel/src/graph_*.rs`) and the scheduler is its own module.
- **One shared registry edit, yours, first.** The job-kind enum, the string mapping and the worker
  claim/dispatch arms are shared files that P6 also needs. You make that edit: add the four variants
  and their dispatch scaffolding pointing at your modules, in additive form, keeping `embed_text`
  and `vision_tag` exactly as they are. P6 then appends one variant and one dispatch arm for its own
  module. Never reorder or rename an existing variant (`03 §4` stores the strings in `jobs.kind`).
- **Persistence is additive.** Add `crates/store/src/graph.rs` and the `Store` methods it needs.
  New trait methods carry a default body (copy the `history_readiness` pattern in
  `crates/traits/src/contracts.rs`), so no existing implementation or test fake breaks. Never change
  an existing method's signature or behaviour. One transaction per chunk, and every insert is an
  upsert that respects the table's `UNIQUE` keys.
- **`crates/sessions` is read-only input.** Consume its tool recognition as data, exactly as
  `§7h.2` says. Add a read helper if you need one; do not change a boundary, a confidence, a
  taxonomy version or an output shape. The kernel's `sessions` dependency is currently dev-only
  (`crates/kernel/Cargo.toml`, the `[dev-dependencies]` block); promoting that one line to
  `[dependencies]` is part of this phase's kernel scope, and the call belongs in the job module.
  `crates/graph` never calls it: the job passes the recognition result in as plain input data.
- **Backfill progress and completion are observable without a new surface.** Progress rides the
  existing setup/job status surfaces (`§7g`, `03 §5`). When the pass completes, the job logs one
  line carrying the five table counts (`entities`, `entity_aliases`, `session_entities`, `threads`,
  `thread_sessions`); that line is the acceptance evidence for "counts pasted", together with a
  second pass that leaves the counts unchanged. Do not add a command, route or UI to read the
  graph: the read routes are P8 and the screens are P9.
- **No UI, no API, no MCP, no insights.** P5 writes the graph and proves it. The read routes and
  MCP tools are P8; the screens are P9; insights are P8. Do not add a command or a route to see the
  graph, and do not start `insights`.

## Acceptance

Verbatim from the roadmap (`docs/0.4.5.md`, P5):

```
**Acceptance:** entity recovery on the P4 automatic set at or above the thresholds frozen at
Gate A; backfill over the real DB completes with counts pasted; determinism test (same input →
same threads); override precedence tests.
```

Decomposed:

- [ ] The P4 harness runs against the built app and reports entity recovery at or above the Gate A
      threshold, with the report pasted verbatim into `specs/05_BUILD_REVIEW.md` (the maintainer's
      real-DB run; the agent's synthetic run is pasted separately and labelled as a fixture).
- [ ] The backfill completes over the real database, with per-table row counts for `entities`,
      `entity_aliases`, `session_entities`, `threads`, `thread_sessions` pasted verbatim; a second
      run over the same database changes no count (idempotence).
- [ ] A determinism test feeds the same input twice, and once with shuffled session order, and gets
      identical threads, identical `cluster_key` values and identical titles.
- [ ] Override precedence tests cover rename, merge and split, each asserting that the override
      beats the clusterer and that a later override of the same kind beats an earlier one.
- [ ] Extraction tests cover every row of the confidence table, and a test asserts that a
      disabled or absent model leaves the graph unchanged (heuristic entities never depend on it).
- [ ] Linking tests cover the closed interval, the open session and the maximum-confidence rule.
- [ ] `specs/08_CHANGELOG_AI.md` and `CHANGELOG.md` record the addition.

## Maintainer run

The agent has no copy of the real database. Do not invent a recovery number, and do not present a
fixture reading as the Gate A comparison. The phase's real evidence is produced on the maintainer's
machine:

1. Install the build and leave the app running normally. The graph scheduler drains the extraction
   queue on idle; progress appears on the existing setup/job status surfaces.
2. When the backfill completes, copy the completion log line with the five table counts into
   `specs/05_BUILD_REVIEW.md`, then restart the app once and confirm a second pass leaves the counts
   unchanged.
3. Run the P4 harness against the live database (its own `Maintainer run` section gives the exact
   command) and paste the entity-recovery line into `05` beside the Gate A threshold.
4. If the number is below the threshold, that is a stop-and-report, not a tuning session.

## Stop conditions

Halt and ask (append the question and its resolution to `specs/07_KNOWN_GAPS.md` with owner and
date) when any of these happen:

- A product decision the specs do not answer. Record it in `07`; never choose it silently.
- A contradiction between specs. Record it in `specs/06_PATCH_PLAN.md`.
- The work needs a file outside the owned paths above.
- The work needs a schema change. Only P3 touches the DDL: if a column, index or CHECK is missing or
  wrong, stop, amend `03 §4` first, and treat it as a contract change (0.4.5 D2), not a silent fix.
- The work needs a new settings key. The table in `03 §8` is closed (0.4.5 D6).
- The clustering rule cannot express the data you find (for example two components would produce
  the same `cluster_key`). Stop: that is a contract defect in `§7h.4`, record it in `06`.
- A verification command stays red after one genuine fix attempt.
- The entity-recovery number lands below the Gate A threshold. Stop and report: do not tune the
  threshold, do not widen the reference extractor, and do not rename entities until the number
  passes.
