### The IPC glue: read this before writing any code

The screens read Rust data through IPC commands and render `ts-rs` types from `ui/src/bindings`.
`docs/0.4.5.md` §4 assigns **no** phase the `src-tauri` command glue, so before writing anything:

1. Read `ui/src/bindings`. That is the truth about what exists.
2. Check for the capability list: threads list, thread detail, entity list, insight list, the three
   override writes (rename, merge, split), and the Ask conversation reads P6 shipped
   (`ask_threads`, `ask_turns`).
3. If every capability is present, use it and change nothing in `src-tauri`.
4. If one is missing, that is an ownership gap, not something to route around. Record it in
   `specs/06_PATCH_PLAN.md` and message the maintainer with the exact capability and command name.
   Do not invent a command name, do not write a UI type by hand, and do not read the store
   directly (the UI cannot).

If the maintainer grants the extension at kickoff, the only shape that keeps §4's intent is:

- a new file `src-tauri/src/graph.rs` for the graph and conversation commands,
- one contiguous registration hunk in `src-tauri/src/lib.rs` (no other phase in this wave touches
  it; P8 needs no IPC),
- a new `crates/traits/src/graph_ipc.rs` registered by one `pub mod` line in
  `crates/traits/src/lib.rs`, holding the threads, entities and override wire types,
- the regenerated `ui/src/bindings`.

Two collision rules. P8 owns `crates/traits/src/ipc.rs` in this wave for the insight payloads: do
not add graph types there, and reuse any type P8 has already defined rather than adding a second
one for the same shape. If `crates/traits/src/lib.rs` or `src-tauri/src/lib.rs` shows unmerged work
from another executing phase, stop rather than resolve it by hand.

## Contracts you must satisfy

**Work list (`/work`)**

- Threads, sortable by last touched and by time spent; the sort is real, not a re-render of one
  order (`docs/0.4.5.md` P9).
- A row shows title, last touched, session count, and says so honestly when the thread's
  confidence is low (`UI_REFERENCE §4`, Work list row).
- While clustering or backfill runs, rows appear as they land with a counts line ("N of M sessions
  clustered"). That is the partial state, not a spinner over a blank pane.
- Empty is the honest sentence from `UI_REFERENCE §4` ("No threads yet ..."), which is also the
  state when clustering has not run.
- Rename, merge and split write `thread_overrides`. Never write `threads` or `thread_sessions`
  directly: overrides are the only user-authored path and they always beat the clusterer
  (`03 §7h.4`, `§7h.5`).
- Merge names the surviving thread (`target_thread_id`) and states how many sessions move; split
  takes an explicit list of sessions; both confirm before writing because they destroy the current
  grouping (`UI_REFERENCE §4`, Thread page row); rename is non-destructive and undoable through
  the same override path.
- After an override lands, the affected rows re-read from the server. Do not patch the list
  optimistically into a state the server disagrees with.

**Thread page (`/work/:id`)**

- Shows the thread's sessions as a timeline, its entities, its open loops, its connected threads,
  and an Ask scoped to the thread (`docs/0.4.5.md` P9).
- A thread that has been merged away explains the merge and links to the surviving thread instead
  of erroring (`UI_REFERENCE §4`, Thread page row).
- Open loops on this page are `open_loop` insights whose `insight_evidence` includes this thread
  or one of its sessions. That is the only link the schema provides (`03 §7j.2`, `03 §4`), so
  render exactly that and nothing inferred.
- Every claim rendered here (a count, a last-touched line, an open loop, a connection) links to
  the row that proves it. This phase's rule, below, is absolute.

**Insights (`/insights`)**

- Cited cards grouped by the five kinds, with a window picker (`docs/0.4.5.md` P9,
  `UI_REFERENCE §4`, Insights v2 row).
- Each card opens its evidence. The card's typed payload renders without the model; phrasing, when
  present, is additive and never the only text (`03 §7j.5`).
- A partially computed window is labelled as partial. A window with no insights says so. No
  fabricated chart, ever (`UI_REFERENCE §4`).
- No notification, badge, streak, score, grade, or ordering that implies a target (`03 §7j.4`,
  0.4.5 D13).
- Stale rows (`stale=1`) are regenerated by P8's engine; the UI may show them but must not present
  a stale row as current.
- Cutover: when the rewritten route no longer calls `get_insights`, that command and the
  `insights_summary` store aggregate it calls become dead weight and are removed as part of this
  phase, not left behind. `crates/store/src/insights.rs` is P8's file in this wave, so remove it
  only after P8 has merged; if P8 has not merged by the time you cut over, leave the removal for a
  `fix/` branch and record it in `specs/06_PATCH_PLAN.md`. Keep the aggregate if anything else
  still calls it.

**Ask v2 (`/ask`)**

- A conversation view with persisted threads: the thread list, the turns in `ordinal` order, and
  the answer streaming into its turn (`03 §7i.4`, `UI_REFERENCE §4`).
- Every answer turn renders session citations and frame citations from the turn's citation field
  (`03 §7i.3`). A turn with no citation is a defect: do not render it as an answer.
- Scope chips for the time window, the thread and the entity are visible, editable and show the
  window and entities actually applied to the turn (`UI_REFERENCE §4`).
- A follow-up reuses the previous turn's window and resolved entities unless the new question
  overrides them (`03 §7i.4`). The chips must make that reuse visible, not silent.
- Entity scope degrades to plain text when the graph is empty; Ask v2 must work on an empty graph
  (`03 §7i.1`).
- A failed turn keeps the question in the thread with a retry, never a lost turn
  (`UI_REFERENCE §4`).
- Deleting a conversation deletes turns only: never frames, sessions, the graph or insights
  (`03 §7i.4`).

**The evidence rule for every screen**

- Every rendered claim links to its evidence (`docs/0.4.5.md` P9). That means: each insight card,
  each thread-page claim and each ask turn carries at least one navigation to the row that proves
  it.
- `frame` evidence opens the Moment (`/timeline/:id`), `session` evidence opens the Session
  (`/timeline/session/:id`), `thread` evidence opens `/work/:id`, `report` evidence opens the saved
  report. Those four destinations exist in `UI_REFERENCE §3`.
- `entity` and `mark` evidence have **no** route in `UI_REFERENCE §3`. A chip that goes nowhere
  breaks this rule, and inventing a route is forbidden. Stop and record it (see stop conditions).

**Components built here for P10**

- `ConnectionsPanel` and `EntityChips` live in `ui/src/components/intelligence/`, take their data
  as props, and fetch nothing (`UI_REFERENCE §5`). P10 places them in Session and Moment.
- They render on semantic and component tokens only, are keyboard operable, and work in every
  theme the `UI_REFERENCE §1` pick ships (`UI_REFERENCE §2`, §7).

**Cross-cutting**

- Tokens only: no raw hex, no px font size, no magic spacing, no new primitive. Use P2's
  primitives as they are (`UI_REFERENCE §2`, `04` §4).
- Typed IPC only: every payload comes from `ui/src/bindings`; never hand-write an API type; never
  edit a generated binding (`UI_REFERENCE §6`, §10.2).
- TanStack Query owns all server state; no `useEffect` fetch-and-setState (`UI_REFERENCE §6`).
- All five states on every screen: loading, empty, error, partial, populated
  (`UI_REFERENCE §4`, §10.1). No mock data, no dead end, no "Coming Soon".
- Shell rules: one scroll context per route, no nested or horizontal scrollbars, no layout shift on
  data arrival, skeletons reserve final geometry (`UI_REFERENCE §8`).
- Rules of Hooks; every new route has an error boundary (`04` §4, `UI_REFERENCE` §6).
- Copy follows `UI_REFERENCE §9`: plain language, sentence case, actions keep their name.

## Verification, in order

Run the UI first: the Rust build embeds `ui/dist`, so a stale or broken UI bundle invalidates the
Rust steps. One command per line, no `&&`:

```
cd ui
npm ci
npm run lint
npm run build
cd ..
node scripts/stage-mcp.mjs
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo build --workspace
cargo test --workspace
git diff --exit-code -- ui/src/bindings
```

Then the P9-specific checks:

```

wc -l ui/src/routes/Work.tsx ui/src/routes/Thread.tsx ui/src/routes/Insights.tsx ui/src/routes/Ask.tsx

grep -rn 'rename\|merge\|split' ui/src/routes/Work.tsx ui/src/routes/Thread.tsx ui/src/components/intelligence
cd ui

```

What each proves: the files exist under the owned paths; the size line is a readability check, not
a gate; the router grep shows the three entries registered; the override grep shows the three write

Paste the raw output of every command into `specs/05_BUILD_REVIEW.md`, and the phase record into

## Stop conditions

Stop and ask, and record the item where indicated, when:

- a product decision is needed that the specs do not answer: log it in `specs/07_KNOWN_GAPS.md`;
- the specs contradict each other: log it in `specs/06_PATCH_PLAN.md`;
- the work needs a file outside the owned paths, including `crates/`, another phase's UI paths, or
  a hand edit of `ui/src/bindings`;
- a schema change outside P3 is needed (0.4.5 D2, `03 §4`);
- any verification command stays red after a genuine fix attempt (`04` §6).

P9-specific, and these are live:

- **`connected threads` is undefined.** `UI_REFERENCE §3` says the Thread page shows connected
  threads; neither `§7h` nor `UI_REFERENCE` defines the relation or its order. Do not guess. Log
  the candidate reading (threads sharing at least one entity, ordered by shared-entity count then
  last touch) in `specs/06_PATCH_PLAN.md` and stop for the maintainer.
- **`time spent` is undefined.** The Work list sorts by it, and no spec says how thread time is
  computed (sum of session durations, wall clock across sessions, something else). Do not pick
  one silently; record it and stop.
- `entity` or `mark` evidence has no destination route in `UI_REFERENCE §3`, so the evidence rule
  cannot be satisfied for a card whose only evidence is one of those. Record both readings (a
  context label that does not navigate, or a filter link into Work or Recall) and stop.
- A needed IPC command or binding type is missing (the ownership gap above). Do not create a
  command, a type or a route to get past it.
- P8's typed payload for a kind is not in `ui/src/bindings` at your base. Do not render a guessed
  shape; the payload is P8's contract and it is additive.
- P6's ask-turn persistence is not in the bindings at your base, so the conversation view cannot
  be built as specified.
- A screen needs a new route. The route set in `UI_REFERENCE §3` is the contract.
- A design choice would need a new token or a new primitive: both are P2's contract.

## Do not

- No stubs, no placeholder screens, no mock data, no "Coming Soon" (`04` §4, `UI_REFERENCE` §10.1).
- No hardcoded expected values in tests.
- No weakening of a test or a lint rule to get green. If a rule is wrong, stop and say so.
- No citation that points at a row that does not exist, and no answer rendered without its
  citations.
- No chart, ranking or count presented without evidence behind it.
- No notification, badge, streak, score or grade, on any screen (0.4.5 D13).
- No direct write to `threads` or `thread_sessions`: overrides only (`03 §7h.5`).
- No commits to `main`, no push, no merge, and no commit or push at all until the maintainer
  validates the content and names the target repo `nicolasestrem/screensearch` (0.4.5 D18).
