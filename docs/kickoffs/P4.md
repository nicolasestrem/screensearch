## Contracts you must satisfy

- **Read-only, structurally.** Every DB handle opens with `SQLITE_OPEN_READ_ONLY` (the
  `crates/harness/src/export.rs` pattern), sets a busy timeout for the live WAL database, and issues
  only SELECTs. The runner never creates a table, never migrates, never writes to the DB, and never
  needs a `-wal`/`-shm` file of its own. A test must attempt a write through the runner's handle and
  assert that it fails.
- **No product implementation crates.** `crates/harness` may add `traits` (wire types only),
  `reqwest`, `tokio`, `futures-util`, `serde`, `serde_json`, `toml`, `chrono` and dev-only
  `wiremock`/`tempfile`. It must **not add** a dependency on `store`, `kernel`, `inference`, `api`,
  `mcp` or `graph`: linking `store` would open the database read-write and destroy the guarantee
  above. The crate's own header records that it is never shipped, and `03 §2`'s dependency rule
  keeps module crates off each other's concrete implementations. The existing dev-only `sessions`
  dependency (the `--algo shipped` segmentation adapter) stays exactly as it is and does not grow.
- **Measure the product, do not re-implement it.** Ask is measured through the running app's local
  HTTP API: `POST /v1/ask` for answers, citations and latency, and `GET /v1/search` for the
  retrieval arm (`03 §7c`). The bearer token is the `api.token` row read from the read-only `settings`
  table, since the write/ask surface requires it; if it is absent, fail with a message naming
  Settings > Integrations instead of guessing.
- **Five generators, exactly these.** Each pair is derived mechanically from the DB; the question
  text is generated from the same facts. A pair carries the generator name, the question, the
  expected frame ids, the expected session ids, the expected strings (the reference strings the
  generator derived, used to check that the answer contains the known fact), and the window the
  question implies (a pair with no window means the whole history).
  - *last-seen*: "When did I last have `<file / document / domain>` open?" Ground truth: the maximum
    `frames.captured_at` among frames whose `window_title`, `browser_url` or content text contains
    the reference string.
  - *involvement*: "Which sessions involved `<repo / domain>`?" Ground truth: the `sessions.id` set
    of frames matching the string, ordered by `started_at`.
  - *sequence*: "What was I doing before session `<Z>`?" Ground truth: the session with the greatest
    `started_at` below `Z`'s, plus that session's dominant reference string.
  - *window recall*: "What did I work on <date, morning>"? Ground truth: the sessions whose interval
    overlaps the local morning window, plus their dominant reference strings.
  - *seen-again*: "Where else did this text appear?" Ground truth: the frames returned by exact FTS
    matching of a sampled distinctive string (a string of at least 24 characters that occurs in
    more than one frame and in no more than a bounded number of frames).
- **Several hundred pairs per run, regenerated per run.** Default 300 pairs, 60 per generator, with
  a deterministic redistribution of any generator's deficit (a generator with fewer eligible units
  takes what exists; the deficit goes, in fixed generator order, to the others). Nothing is read
  from a committed file. `--pairs` overrides the total.
- **Deterministic for a given DB and seed.** The workspace has no `rand` dependency: implement one
  small seeded PRNG inside the crate (SplitMix64 or equivalent), use it for every sampling decision,
  and make the run reproducible from `(db, seed)`. The default seed is the run start time in unix
  ms and is printed in the report; `--seed` pins it.
- **The reference entity extractor is independent and narrow.** It extracts only what is
  unambiguous by construction: an absolute Windows path with a drive letter, a full URL with scheme
  and host, a repository identity of the form `<host>/<owner>/<repo>` (from a URL, a git remote or a
  terminal cwd), a document name ending in a document extension, and issue/PR references (`#123`,
  `ABC-123`). It carries kinds from `03 §7h.1` only. It is not shared with `crates/graph` and must
  not import it: the independence is the point of the check.
- **Five metrics, defined here so P5 and P6 are measured identically.**
  - *Evidence recall@10*: per pair, the fraction of the pair's first 10 expected ids that appear in
    the turn's cited ids; aggregate is the mean over pairs, reported overall and per generator.
    Cited ids are the cited frame ids plus, when the stream carries them, the cited session ids; an
    expected session id also matches when a cited frame's `session_id` equals it. This is the
    comparator Gate A freezes, because the product exposes retrieved evidence to a client only as
    citations (`03 §7i.3`).
  - *Retrieval recall@10 (diagnostic)*: per pair, whether the pair's first expected frame id appears
    in the first 10 `frame_id`s returned by `GET /v1/search` for the question text with
    `limit=10` and `include_chrome=false` (the arms Ask itself uses). Reported next to the
    comparator, never mixed into it.
  - *Citation validity*: invalid cited ids divided by total cited ids. A cited frame is valid when it
    exists and its `captured_at` lies inside the pair's window (a pair with no window means the whole
    history); a cited session is valid when it exists and its interval overlaps the window. Every
    invalid id is printed with its pair.
  - *Known fact present*: the answer text, lowercased and whitespace-collapsed, contains at least
    one of the pair's expected strings; for last-seen pairs the expected local date
    (`YYYY-MM-DD`) also counts. Rate over pairs, per generator.
  - *Latency p50 and p95*: per turn, from POST to the terminal `done` or `error`, wall clock in ms,
    over successful turns only; failures are counted separately by class
    (`api_unavailable`, `timeout`, `empty_answer`, `http_error`).
  - *Entity recovery and invention*: over the reference entities found in the sampled frames,
    recovery is the fraction matched by `entities.canonical_name` or an `entity_aliases.alias`;
    invention is the count of `entities` rows whose `canonical_name` and every alias appear in no
    frame's `window_title`, `browser_url` or content text. On a DB where the work-graph tables are
    empty (the P3 state), report the literal string `n/a (no entity surface)`; never print a
    fabricated zero that reads as a measurement.
- **Report shape.** One Markdown document to stdout and to
  `harness-data/eval-<run-id>/report.md`, plus `pairs.jsonl` and `runs.jsonl` beside it
  (`/harness-data/` is already git-ignored). The report states the seed, the DB path, the API base
  URL, the pair count per generator, the five metrics overall and per generator, every invalid
  citation, every failure, and an empty "Gate A threshold" column for the maintainer to fill.
  `pairs.jsonl` carries every pair with its question, expected ids and expected strings, because
  later phases read it: P9 asks 10 questions from this set through the UI at Gate C
  (`03 §13d` item 9). `--pairs 10 --seed <n>` must therefore produce a small, reproducible subset
  against the live database, and `--pairs` must never change how a pair is generated, only how many.
  `runs.jsonl` records one line per turn: the pair id, the timing, the cited arrays, and the
  terminal event's payload passed through verbatim, so a field added to that event by a later phase
  (P6 adds stage counts and the token total) is readable without changing this crate.
- **Forward-compatible citation reader.** Today the stream emits one `citation` event per cited
  frame. P6 (0.4.5 D12, `03 §7i.3`) adds one terminal `citations` event carrying
  `{"sessions":[id...],"frames":[id...]}` plus its own diagnostics, and keeps every existing event
  byte-identical. Read both shapes now, in one place: when the terminal event is present use its
  two arrays and ignore any other field, otherwise use the frame `citation` events. On today's
  stream the two produce the same frame set, so the baseline is not affected. Cover the future shape
  with a stubbed-stream test.
- **D17 fence, absolute.** No hand-written question set, no labels, no answer key, no golden file,
  no "a few examples to seed the generator". Every pair comes from a DB query at run time. If you
  find yourself drafting a question list, asking the maintainer for questions, or adding a checked-in
  fixture of expected answers, you have misread the task: stop and re-read this bullet. The only
  fixtures allowed are synthetic databases you build in tests to prove the generators respond to
  data, plus stub HTTP responses that exercise the reader.
- **Zero maintainer input to run it.** No prompt, no file to author, no labelling, no
  spot-checking during the run. The maintainer's only part is the run itself on his machine (below).

## Maintainer run

The agent has no copy of the real database, no answer model and no running app. It must never
invent baseline numbers. It proves the runner on a fixture and pastes that report into `05` clearly
labelled `fixture (not the baseline)`. The baseline is produced by the maintainer on his machine:

1. Build the harness once: `cargo build -p harness`.
2. Start the app on v14, wait until the answer model is loaded, and enable the API in
   Settings > Integrations (port `43210` by default). The runner reads `api.token` from the database
   itself, so no token is ever passed on the command line or stored in the repo.
3. Run, with the live database at `%APPDATA%/app.screensearchv2c.desktop/screensearch.db`:
   `cargo run -p harness --bin harness -- eval --db "%APPDATA%/app.screensearchv2c.desktop/screensearch.db" --api http://127.0.0.1:43210 --out harness-data/eval-baseline`
4. Paste `harness-data/eval-baseline/report.md` into `specs/05_BUILD_REVIEW.md` verbatim, then fill
   the Gate A threshold column together with `specs/06_PATCH_PLAN.md`. The run output stays in
   `harness-data/` and is never committed.
5. Re-running later at Gate C is the same command with a new `--out`: the generators regenerate
   pairs from whatever the database holds then, so the set never goes stale.

If the database is the live one while the app runs, the read-only connection and busy timeout are
what keep the run safe; do not copy the database, do not stop the app, and do not close the WAL.

## Stop conditions

Halt and ask (append the question and its resolution to `specs/07_KNOWN_GAPS.md` with owner and
date) when any of these happen:

- A product decision the specs do not answer. Record it in `07`; never choose it silently.
- A contradiction between specs. Record it in `specs/06_PATCH_PLAN.md`.
- The work needs a file outside the owned paths above.
- The work needs a schema change of any kind. P3 owns the DDL (`03 §4`); P4 reads, it never alters.
- The measurement needs a product surface that does not exist (an endpoint, an event field, a
  column). Stop. Do not add it, and do not re-implement retrieval inside the harness to fake
  observability.
- A metric cannot be computed from what the product exposes. Record the exact gap in `06`; do not
  substitute a different metric, and do not report a rounded guess.
- A verification command stays red after one genuine fix attempt.
- You are about to write a question, a label or an answer key. That is D17; re-read the fence.
