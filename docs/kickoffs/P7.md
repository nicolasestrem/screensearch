## Contracts you must satisfy

**Shell**

- Rebuild `NavRail`, `StatusRail`, `CommandPalette`, `QuickActions`, `ReadinessBanner`,
  `UpdateIndicator` and the toast host on v2 primitives and v2 tokens (`UI_REFERENCE §3`, §8).
- Fixed rails, one scrolling pane: only the content pane scrolls, and no route introduces a second
  vertical scroller. Every grid item carries `min-w-0` (`UI_REFERENCE §8`).
- Row height, control height and grid gap come from the one density token; no screen hardcodes a
  row height (`UI_REFERENCE §8`).
- `NavRail` renders its entries from one ordered list in the order `Deck · Ask · Work · Recall ·
  Insights · Settings` (0.4.5 D7). At your base only Deck, Recall, Insights and Settings have
  routes. Do **not** add a rail entry that leads to a missing route and do **not** build a
  placeholder screen: `UI_REFERENCE §10.1` forbids dead ends and "Coming Soon". Leave the ordered
  list exported from `ui/src/app` (route metadata) so P9 adds `/ask` and `/work` in place, in
  Wave C, without restructuring the rail.
- `StatusRail` is telemetry only, one row, chip widths stable (`UI_REFERENCE §8`). The throttle
  chip still appears only at level ≥ 1 and still reflects `throttle_changed`
  (`UI_REFERENCE §3`).
- The palette stays `⌘K`, jump-to plus the existing actions; it must also reach Settings by name
  (`UI_REFERENCE §3`).

**Settings v2, structure**

- Replace `ui/src/routes/Settings.tsx` (1,362 lines today) with `ui/src/routes/settings/`: a
  layout file plus one file per category, named `General.tsx`, `Capture.tsx`, `Privacy.tsx`,
  `Intelligence.tsx`, `Models.tsx`, `Data.tsx`, `Integrations.tsx`, `Advanced.tsx` and an
  `index.tsx` route entry.
- No file in `ui/src/routes/settings/` over about 300 lines (`docs/0.4.5.md` P7). If a category
  exceeds it, split its row components into that same folder, not into `components/shell`.
- Every category uses one row pattern: label, one-line plain-language effect, control, and a
  "changed" marker with reset-to-default (`UI_REFERENCE §3`).
- Controls with real behaviour already exist as components in `ui/src/components/domain` (for
  example `ApiReadTokenControls`, `HotkeyField`, `ModelTierPicker`, `RetentionControl`,
  `ScheduleControl`, `MemoryPanel`, `SetupDetails`). Import them and put them inside your row
  chrome. Do not rebuild their state machines in `routes/settings/`, and do not edit them: that
  path is P10's, and P10 refonts those components. The consequence is deliberate: Settings v2
  ships a v2 shell, v2 rows and these controls as they are today; `UI_REFERENCE §4` says the eight
  categories are a new grouping and a new row pattern, not new contracts for those controls.
- If a control cannot fit a row without changing the domain component, stop and record it. Do not
  duplicate it and do not fork it.
- Autosave per field with an undo toast, no global Save button (0.4.5 D9). A failed save keeps the
  typed value in place, explains, and retries (`UI_REFERENCE §4`, Settings row). Apply
  optimistically and reconcile from the `get_settings` cache.
- The undo toast restores the previous value through the same `set_settings` path; it is not a
  local-only revert. Use P2's Toast primitive.
- Destructive actions sit behind a confirm dialog that names what is destroyed, and never depend
  on the autosave toast (0.4.5 D9; `03 §8` preamble). Inside your surface that is data export and
  history deletion in Data and credential revocation in Integrations. The thread-override reset
  lands in P9; the confirm pattern you build is the one it reuses.
- Live status inline wherever a setting has a runtime effect: hotkey registered or failed, API
  listening on (actual address and port) or bind error, model loaded, throttle level
  (`UI_REFERENCE §3`, §4). A failed hotkey registration is a visible warning plus toast, never
  silent (`03 §8`, D6 of 0.3.2).
- The eight categories are a regrouping, not a renegotiation: the API, throttle, App and Models
  setup contracts keep their existing behaviour and states (`UI_REFERENCE §4`, the paragraph
  after the state table).

**Settings v2, the closed key set**

- The UI renders exactly the 25 rows whose `Disposition` is `UI` in `03 §8`, and nothing else may
  appear as an editable control. The ceiling is binding (0.4.5 D6). The 25 are:
  `answer.thinking`, `api.bind_address`, `api.enabled`, `api.port`, `api.token`,
  `app.close_to_tray`, `app.run_at_startup`, `capture.interval_ms`, `capture.monitors`,
  `enrich.vision_timer_enabled`, `enrich.vision_timer_interval_ms`, `marks.hotkey`,
  `models.answer_tier`, `models.vision_tier`, `overlay.hotkey`, `privacy.excluded_apps`,
  `privacy.pause_on_lock`, `reports.daily_top_k`, `retrieval.default_top_k`,
  `sessions.gap_close_secs`, `sessions.min_len_secs`, `storage.max_width`,
  `storage.retention_days`, `text.include_chrome_default`, `throttle.enabled`.
- Their `Where` column is the category: General, Capture, Privacy, Intelligence, Models, Data,
  Integrations, Advanced. `throttle.enabled` is a `UI` key whose home is **Advanced**; the eight
  throttle threshold keys are `file-only` and are shown read-only beside it.
- `api.token` shares one credential row with the read credential (`api.read_token` is not a
  separate UI key). The read credential is written only through the create / rotate / revoke /
  reveal commands, never through `get_settings` / `set_settings` (`03 §8`, `03 §7f`).
- `file-only` keys are shown **read-only** under Advanced with the `advanced.toml` path: app data
  dir, next to `screensearch.db`, one `[section]` per key prefix with the suffix as the field
  name (`03 §8`).
- `deleted` keys appear nowhere in the interface. No retired key is tolerated: a settings file
  with an unknown key is rewritten once with it removed, with no error and no migration; that is
  P3's code path, not a UI behaviour, and the UI simply never renders such a key (`03 §8`, load
  rule).
- Do not rename a key, add a key, or change a default. That is a `03 §8` / P3 change, and P3 has
  merged; a need for it is a stop condition.

**Settings v2, search and keyboard**

- One search field over all settings that finds every setting **by label and by key name**
  (gap #103, absorbed by this phase; `UI_REFERENCE §3`).
- Search must stay usable from the keyboard, must not lose the current category on escape, and its
  empty result is an invitation ("no setting matches ..."), never a blank pane.
- A keyboard-only pass through all eight categories must be possible: sidebar reachable, every
  control focusable, visible focus ring, no focus trap (`UI_REFERENCE §7`, §10.5).

**Cross-cutting**

- Tokens only. Semantic and component tokens, no raw hex, no px font size, no magic spacing
  (`UI_REFERENCE §2`, `04 §4`).
- Typed IPC only: every payload comes from `ui/src/bindings`. Never hand-write an API type; never
  edit a generated binding (`UI_REFERENCE §6`, §10.2).
- TanStack Query owns all server state; no `useEffect` fetch-and-setState (`UI_REFERENCE §6`).
- Every category defines all five states (`UI_REFERENCE §4`). No mock data, no dead end, no
  "Coming Soon" (`UI_REFERENCE §10.1`).
- Rules of Hooks: all hooks before any early return; a route error boundary stays in place
  (`04 §4`).
- Copy follows `UI_REFERENCE §9`: name the control by what the user controls, sentence case, no
  filler.

## Verification, in order

Run the UI first: the Rust build embeds `ui/dist`, so a stale or broken UI bundle invalidates the
Rust steps. One command per line, no `&&`:

```
cd ui
npm ci
npm run lint
npm run build
cd ..
node scripts/stage-mcp.mjs
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo build --workspace
cargo test --workspace
git diff --exit-code -- ui/src/bindings
```

Then the P7-specific checks:

```
test ! -f ui/src/routes/Settings.tsx
wc -l ui/src/routes/settings/*.tsx
grep -rnoE '"[a-z_]+\.[a-z_0-9]+"' ui/src/routes/settings | sort -u
grep -rn 'tokens.compat' ui/src
cd ui
npm test
cd ..
```

What each proves: the first that the old wall is gone; the second the file-size rule; the third
the complete set of key literals in the new folder, which must be a subset of the 25 `UI` rows plus
the `memory.*` keys documented in `03 §8c`/`§8d`; the fourth that the only reference to the P2 shim
is the single import in `ui/src/styles/globals.css` (P2's, deleted by P10), because any other
reference means a screen is bypassing the token layer; the last that the existing UI tests still
pass.

Do not treat a green `npm run build` as acceptance. Screenshots and the pasted tables are the
acceptance (`04` §6, `UI_REFERENCE` §10.8).

Paste the raw output of every command into `specs/05_BUILD_REVIEW.md`, and the phase record into
`specs/06_PATCH_PLAN.md`, `specs/07_KNOWN_GAPS.md`, `specs/08_CHANGELOG_AI.md` and `CHANGELOG.md`
(`04` §7).

## Stop conditions

Stop and ask, and record the item where indicated, when:

- a product decision is needed that the specs do not answer: log it in `specs/07_KNOWN_GAPS.md`;
- the specs contradict each other: log it in `specs/06_PATCH_PLAN.md`;
- the work needs a file outside the owned paths, including any edit to `crates/`, `src-tauri/`,
  `crates/traits`, `ui/src/bindings` or another phase's route file;
- a schema change outside P3 is needed (0.4.5 D2, `03 §4`);
- any verification command stays red after a genuine fix attempt (`04` §6).

P7-specific, and each of these is live:

- **The density token is a contradiction.** `UI_REFERENCE §8` says `compact` is "a choice in
  Settings", and `03 §8`'s closed 25-key set contains no density key, while `04 §4` forbids an
  unattributed setting. Do not invent a key and do not silently drop the choice. Log the
  contradiction in `specs/06_PATCH_PLAN.md` with the two candidate readings (a new `file-only`
  or `UI` key, or a per-window preference that is not a setting) and stop for the maintainer.
- `UI_REFERENCE §1` does not yet carry the D4 pick at your base. Nothing visual starts before it
  (0.4.5 D4).
- A row needs a control P2's primitives do not offer. Do not build a private control inside
  `components/shell`; that recreates the primitive layer outside the design system.
- A row needs a new IPC command or a new field in the `Settings` struct. That is the settings
  model, which P3 owns and has already merged. Record it in `specs/06_PATCH_PLAN.md` and stop.
- A `UI` key turns out to have no live consumer. Do not delete it yourself and do not demote it:
  the disposition table is P3's and the ceiling is a maximum, not a target (0.4.5 D6). Record it
  and stop.
- The read credential or a `memory.*` control cannot be built from the commands listed in `03 §7`
  and `03 §7f` without a new command.
- A settings search that satisfies "finds every setting by label and by key" would need a
  server-side index or a new command.

## Do not

- No stubs, no placeholder components, no mock data, no "Coming Soon" (`04` §4, `UI_REFERENCE`
  §10.1).
- No hardcoded expected values in any test.
- No weakening of a lint rule, an eslint config or a test to get green. If the rule is wrong, stop
  and say so.
- No global Save button, and no save-on-blur that hides a failed write (0.4.5 D9).
- No new setting, no renamed key, no changed default, no retired-key tolerance in the UI.
- No commits to `main`, no push, no merge, and no commit or push at all until the maintainer
  validates the content and names the target repo `nicolasestrem/screensearch` (0.4.5 D18).
