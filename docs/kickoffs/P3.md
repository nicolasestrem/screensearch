Wave A of the 0.4.5 arc, and it feeds Gate A and the release tag **`v0.4.3`**. It touches no screen and adds no intelligence: it cuts one clean schema and one honest settings model for a single user. This file is the whole instruction for the phase. You do not need the roadmap.

## Contracts you must satisfy

### Baseline schema (0.4.5 D2)

- `crates/store/src/schema.rs` holds **one baseline script** that creates the whole v14 database, and `LATEST_SCHEMA_VERSION` becomes `14`. `03` §4 is the authority for every table it defines.
- The migration chain is **deleted, not emptied**: no `MIGRATIONS` list, no per-version SQL, no version loop, no `PRAGMA foreign_keys=OFF` migration dance, no `LATEST_SCHEMA_VERSION is out of sync with MIGRATIONS` assertion. The v1 to v13 SQL lives in git history and `CHANGELOG-ARCHIVE.md`; it must not remain in the tree (`03` §4).
- The populated-DB migration tests go with it: delete the migration test module in `crates/store/src/lib.rs` and the helper that applies migrations up to a chosen version. Do not rewrite them as baseline tests; write the baseline tests below instead. There are no populated-DB migration tests in this arc (0.4.5 D2).
- Opening a store does exactly two things: if there is no `screensearch.db`, create it from the baseline and write `schema_version = 14` in the same transaction; if there is one, read its version and **require 14**. Anything else (older, newer, missing table, empty file) fails to open with a message that names the found version and the rebuild tool `ssv2c-rebuild` (`03` §4).
- Merging `03` §4 with the current tree has one seam: §4 does not define every table the store creates. The report tables (`report_runs`, `report_deliveries`, `report_files`) and the raw-text search table (`frame_text_raw_fts`) are created by migrations today and are not in §4, while §8c says the exact report DDL belongs in the store module. Carry those tables into the baseline **unchanged**, because the v14 schema is v13 plus exactly the eleven new tables: the arc adds tables, it does not reshape the old ones. Record the §4 omission in `specs/06_PATCH_PLAN.md` as a documentation gap and say so in the phase notes. This is the one place where you proceed rather than halt, because both readings produce the same file; anything that would change behaviour is still a halt.
- `03` §4's eleven new tables (`entities`, `entity_aliases`, `session_entities`, `threads`, `thread_sessions`, `thread_overrides`, `session_vectors`, `insights`, `insight_evidence`, `ask_threads`, `ask_turns`) are created **empty**. Nothing writes them, reads them from a command, queues a job for them or exposes them over IPC in this phase (P5, P6 and P8 do). Do not add store query modules for them.
- Create the `vec0` table through the same open path that already registers `sqlite-vec` for `embedding_vectors`; a baseline test that opens a plain `rusqlite` connection without the extension will fail, and that failure is the test being wrong, not the schema.
- Keep the connection pragmas the store already sets (WAL, foreign keys, recursive triggers, busy timeout, `no_proxy` equivalent behaviour around anything network: P3 adds no network).

### Rebuild tool, `ssv2c-rebuild` (0.4.5 D3)

- It is a **dev-only** binary. Workspace crates are never bundled by the NSIS installer, so being a workspace member is fine; what is not fine is being a dependency of `src-tauri` or of any shipped crate, or shipping in the installer's file list.
- The source database is opened **read-only** (`SQLITE_OPEN_READ_ONLY`; no write, no `PRAGMA` that mutates, no `VACUUM`, no WAL checkpoint on it). After a run, the source file's bytes and modification time are unchanged, and a test asserts both.
- The destination must **not exist**. The tool writes a fresh v14 file, never upgrades in place.
- It copies, as rows, exactly the carry set: frames, images (by path, and it must report a missing image file rather than silently dropping the row's path), content and raw text, text embeddings, sessions, session artifacts, marks, report runs and saved reports, API history/allocator metadata, and read tokens.
- It does **not** copy the transient or derived tables: `jobs`, `chrome_text_catalog`, and the FTS5 / `vec0` index structures. FTS5 and `vec0` indexes are repopulated from the copied source rows (external-content FTS `rebuild`, `vec0` row inserts), never by copying their shadow tables blindly.
- Settings rows: copy the keys that appear in the `03` §8 table plus the reserved keys `03` §7f.8 protects (`api.history_id` and the allocator high-water); drop the nine `deleted` keys. This follows from D6's load rule (a row naming a key outside the table is removed) and from §7f.8 (identity is carried, never recomputed). The allocator counter is copied, **never recomputed from `MAX(frames.id)`**.
- The destination is verified, not assumed: `PRAGMA integrity_check` is `ok`, `PRAGMA foreign_key_check` is empty, `schema_version` is 14, and every table's row count is printed.
- The tool prints a per-table count report for any database (`--counts <path>`) and prints N random frame ids from the rebuilt file (`--sample-frames 20`), because the acceptance needs both and neither may come from a hand-typed query.
- **The tool never renames the source.** `*.v13.bak` is a step the maintainer performs after he confirms the new file opens (0.4.5 D3). If you implement a flag that performs the rename, it stays opt-in, off by default, and it is documented as maintainer-only.
- Everything it does not carry is dropped and re-derived: the eleven new tables are empty in the output, and the phase notes say so.

### Rebuild tool test fence (critical)

- The rebuild tool is tested **only** against a synthetic v13 fixture database built inside the test, with SQL written by the test (frames, text, an embedding, a session, an artifact, a mark, a report run with its file row, a history/allocator pair, a read token), in a temporary directory that the test creates and removes.
- It is **never** tested against a real database, a copy of one, a path outside the repository, `%APPDATA%`, the maintainer's profile, or any file that another phase or another process produced. No test may read an environment variable that points at a real profile.
- If a fixture value is needed, the test writes it. Nothing is copied from real history, and nothing from real history is committed (`04` §4: never commit DBs or secrets).

### Settings v2 (0.4.5 D6)

- The typed `Settings` struct becomes the **UI surface**: exactly the keys whose Disposition is `UI` in `03` §8, with the defaults, clamps and value ranges from that table. The closed set is 26 keys and it is a ceiling: never promote a replacement into `UI` to fill a slot. It was 25 in the P1 contract; the 0.4.5 P2 pick (2026-11-04) raised it to 26 by adding `ui.appearance` (theme select, six kebab-case values, default `pine-light`), which this phase lands as a typed field plus persistence. `api.token` and `api.read_token` stay outside the typed struct and share one UI row; `app.tray_toast_done` stays a direct KV marker outside the struct.
- The nine `deleted` keys are removed from `crates/traits` and from every consumer: `api.network_notice_state`, `capture.event_on_click`, `capture.event_on_clipboard`, `capture.event_on_scroll_stop`, `capture.event_on_typing_pause`, `capture.event_typing_pause_ms`, `capture.uia_run_on_interactive`, `enrich.image_embeddings`, `storage.jpeg_quality`. After the phase the names survive only in the single retired-key list that performs the rewrite below, the doc comments that explain why each retired, and the test that exercises the rewrite. No typed field, no read, no branch, no route, no schema statement.
- The `file-only` keys move out of the typed struct into one typed advanced configuration, loaded once at startup from **`advanced.toml`** in the app data directory next to `screensearch.db`: one `[section]` per key prefix that has at least one `file-only` key, with the suffix as the field name. Exactly eight sections carry values: `[capture]`, `[enrich]`, `[overlay]`, `[reports]`, `[resume]`, `[sidecar]`, `[text]`, `[throttle]`. Every other prefix in `03` §8 is either `UI` or `deleted`, so it gets no section. `app.tray_toast_done` is the 44th `file-only` row but it has no `advanced.toml` home: `03` §8 gives its `Where` column a dash (no file home) and says it is written directly to the `settings` table and read at tray init (`specs/07_KNOWN_GAPS.md`, P1 entry (e)), so it stays a direct KV marker with no `[app]` section. Defaults and clamps come from the `03` §8 table. There is one source of truth per value: no field may remain both in the typed `Settings` and in the advanced file.
- Every consumer of a moved field reads it from the advanced configuration. Behaviour does not change: same defaults, same clamps, same startup timing. `sidecar.idle_ttl_secs` and `sidecar.recycle_rss_mb` are resolved once at supervisor construction and that stays true (`03` §8 rows).
- **No load tolerance** (`03` §8, Load rule): a `settings` row or an `advanced.toml` entry naming a key that is not in the table is rewritten once with that key removed, with no error, no migration and no field kept parsed-but-unused. An unknown section or field in `advanced.toml` is dropped on the same rewrite, so the file always matches the table. A missing or unreadable `advanced.toml` is not an error: defaults apply and the reason is logged, which is the honest degraded path P7 displays.
- The reserved-metadata protections in `03` §7f.8 survive untouched: the rewrite, the retired-key purge, the settings reset and the generic KV delete must never touch `api.history_id`, the allocator high-water or any other reserved key. Keep the existing guard tests for that and extend them to the new loader if the seam moved.
- Regenerate `ui/src/bindings` from the changed types with the existing `ts-rs` export (`cargo test` writes them; `#[ts(export, export_to = "../../../ui/src/bindings/")]` is already on the types). Never hand-edit a binding, and never hand-write a replacement type in the UI.
- Name, in the phase notes, the read-only projection P7 will use to display the `file-only` keys under `Settings · Advanced` (the `UI_REFERENCE` §4 row requires the values and the file path to be displayable). Do not add a second editable surface for them.
