## Summary

ScreenSearch 0.4.6 is a stabilisation release. The headline fix is the startup crash that made the
installed 0.4.5 build fail to become usable on most launches: the main window could ask for the
update status before the updater state existed, and the app aborted with a panic instead of showing
a window. The updater state is now registered before any window is created, so that order cannot
happen. The rest of the release is small: the throttle readout in Settings > Advanced catches up as
soon as you save, the reset-to-default markers read their defaults from the app itself, and a stale
schema comment that listed two of the eight job kinds is corrected.

Nothing else changed in this branch: no new setting, no migration, and no change to capture,
retrieval, the API or the MCP server. The release also carries the memory-pressure relief that
merged into `main` before this branch (the throttle now watches host memory and commit charge, and
level 2 releases the vision model). That work shipped with its own records and gate; this branch's
gate covers only the fixes below. `CHANGELOG.md` has the detail for both.

## Fixed

### Startup no longer crashes before the window is usable

The installed 0.4.5 build often exited almost immediately with
`state() called before manage() for screensearch_lib::update::UpdaterState` (Windows error
`3221226505`). The main window and its overlay are created before the app's own setup code runs, and
the update indicator asks for update status as soon as it mounts. If that question arrived before the
updater state had been registered, the app panicked and never became usable; retrying usually worked,
which made it look like a flaky start.

The updater state is now registered while the app is being built, before any window or webview
exists, so the question can arrive at any time. A regression test builds the app through the same
path and reads the same state the command reads; it fails with the production message if the old
ordering is restored. A 20-launch cold-start series in an isolated profile came up every time with no
panic, and the full ordered build and test chain is green.

### Settings > Advanced: the throttle readout updates as soon as you save

Saving any setting refreshed the settings, hotkey and API status, but not the throttle status, so the
readout could keep showing the pre-save throttle state until the next pressure sample. A save now
refreshes the throttle status too, and the readout takes its on/off line from the saved switch. Turning
the throttle off shows the off line at once; turning it on keeps the honest "waiting for the first
pressure sample" state until a measurement exists instead of printing a stale value.

### Settings: reset markers read the app's own defaults

The "changed" marker on a settings row and the reset action compared against a copy of the defaults
kept in the interface. That copy is easy to fall out of step with the app. The app now serves its
defaults over the same local bridge the interface already uses, and the interface prefers those; the
old copy remains only as a placeholder while that answer is in flight. A test compares the app's
answer against the declared default of each of the 25 rows that store a value (the 26th row stores
no setting), so a default that changes without the interface following fails the build.

## Documentation

- The `jobs.kind` comment in the schema and in the production spec listed two of the eight job kinds.
  Both now list all eight and point at the enum that defines them.

## Upgrade

Install 0.4.6 over 0.4.5. No database migration, no re-capture and no re-index: the schema, the
settings keys and the on-disk layout are unchanged. The updater offers this build through the same
GitHub Releases endpoint as before.
