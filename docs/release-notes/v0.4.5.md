## Summary

ScreenSearch 0.4.5 turns captured history into a memory you can work with. Your captures are now
grouped into **threads** built automatically from the repositories, files, sites, documents and
tickets that appear in them; **Ask** plans a question before it retrieves, cites both the sessions
and the frames it read, and keeps a conversation so a follow-up inherits the previous window and
scope; **Insights** states five kinds of claim about your history where every row carries the
evidence that supports it; and the whole interface is rebuilt on one token set as the **Logbook**
design, with four themes and a Settings screen you can search and edit one row at a time. It is
still the same local-first Windows app: capture, OCR, embeddings and inference all run on your
machine, the API and MCP server stay opt-in, and nothing is uploaded. This release needs a fresh
database (see Breaking).

## What's new

### Work: threads built from repos, files, sites and tickets

On idle and at startup, model-free rules read what was already captured - window titles, browser
URLs, file and repository paths, document names, ticket references and the recognized tool - and
persist deduplicated entities, their links to sessions, and deterministic threads. A thread is a
cluster of sessions that share a strong entity inside a 30-day decaying window.

- `/work` lists the threads, with last-touched and session count, sortable by either and filterable
  by entity; the header says how much of the history is clustered so far instead of implying it is
  complete.
- `/work/:id` opens one thread: its session timeline, the entities those sessions touch, the open
  loops it still holds with their evidence, the other threads it connects to through shared
  subjects, and Ask scoped to that thread.
- Rename, merge and split are written to `thread_overrides` with a receipt and applied by the
  clusterer, so your edit keeps beating the automatic grouping across re-runs.
- Everything in the graph is derived and recomputable: clearing it loses no evidence. There are no
  scores, badges or streaks, and a thread that clustered only on weak links says so in one muted
  line.
- On the committed evaluation fixture the work graph recovers **90.3%** of entities against the
  frozen **80.0%** acceptance threshold.

### Ask v2: time-aware, multi-turn, cites sessions and frames

Ask now plans before it retrieves.

- **Planning.** Relative time phrasing ("yesterday", "last week", "this morning") becomes an
  explicit half-open window in system-local calendar terms, and an entity mention resolves through
  the work graph so retrieval is scoped to the sessions linked to it. A question with no resolvable
  time intent carries no window rather than a fabricated bound.
- **Staged retrieval.** Threads, then sessions (full-text over titles and summaries fused with
  session-vector similarity), then frames inside the winning sessions - each stage only narrowing
  the previous one.
- **Both kinds of citation.** Every answer cites the frames it actually read and the sessions those
  frames belong to.
- **Conversations.** A question starts a conversation and turn 1. Asking again with the conversation
  reuses the previous turn's window and entity scope, so "and the day before?" moves the window and
  keeps the scope; the UI shows an "Inherited from the previous turn" chip so the reuse is visible.
  Turns are persisted, retry reads the failed turn's own recorded scope, and deleting a conversation
  touches no captured evidence.
- **A new background lane.** `session_embed` keeps the session-vector index warm in bounded batches
  on idle and on demand, under the existing pressure throttle, never on the capture path.
- **Degrades honestly.** With empty graph tables and no session summaries, Ask falls back to the
  frame-level search restricted to the planned window.

### Insights: five kinds, every one with evidence

`/v1/insights` and the Insights screen serve typed, evidenced statements about a half-open window:
**thread activity**, **open loops**, **recurrence**, **semantic neighbours** and **resumption**.
Each payload renders completely without a model.

- Every row carries at least one evidence reference (`frame`, `session`, `thread`, `entity` or
  `mark`), enforced inside the store's write transaction; a row whose evidence has gone is reported
  as stale rather than asserted as current, and readers compute that flag with the same predicate
  the sweep writes.
- Generation is one job kind under the existing worker pool, pressure throttle and idle gate. A
  failed pass logs and degrades silently. There are no notifications, badges or targets.
- Saved daily reports and weekly synthesis may cite the window's insights through a deterministic,
  capped context block; with no insights the prompt is byte-identical to before.

### The Logbook design, in four themes

- One token set: primitives, a four-theme semantic layer (**Pine** light and dark, **Ink** light and
  dark, Pine light by default, each with a follow-the-system variant) and a density token.
- Fonts ship as bundled local variable files, so no page loads a remote font.
- 30 primitives and one local icon set are rebuilt on it, and two tests enforce AA contrast in every
  theme and forbid raw colours or pixel font sizes in components.
- Timeline, Session, Moment, Recall, Deck and Settings are rebuilt on those tokens with their five
  states intact. The timeline's scan-head is now a density ribbon whose heights are real capture
  counts, and Session and Moment gained the entity chips and connections panel that Work and Thread
  already had, fed by one additive read.
- The v1 token shim is deleted, and two fences keep it that way: the token test walks all of `ui/src`
  and a lint rule refuses a raw token literal where it is written.
- Initial JavaScript is **112.9 KB** gzip in the main window and **75.4 KB** in the overlay window
  (45% and 30% of the 250 KB budget), and every route is its own chunk.

### Settings v2: eight categories, search, autosave with undo

- **Eight categories** - General, Capture, Privacy, Intelligence, Models, Data, Integrations,
  Advanced - over 26 settings in one row pattern.
- **Every row saves on its own** and offers Undo from a toast. There is no global Save button, and
  saves are serialised: each is built from a freshly read snapshot, so two overlapping edits cannot
  lose one another.
- **Search finds a setting by what it does or by its key**, matching the label, the dotted key, the
  field name and the help text, with the match highlighted; the command palette (Ctrl K) jumps to
  any category.
- **Destructive actions ask first and name the consequence** - including the read-token dialog, which
  states that every agent using that token stops being able to read your history.
- **A category never goes blank:** loading shows skeletons, a failure shows an error with Retry in
  that pane only, and partial data shows the rows it has.

## Breaking

### A fresh database

0.4.5 has **no migration chain**. The database is created from a single baseline at
`schema_version = 15`, and any other version refuses to open with a message naming the dev-only
`ssv2c-rebuild` tool. That tool reads an existing v13 database **read-only** and writes a fresh file
(frames, images, text, embeddings, sessions, marks, reports and the API identity are copied; derived
indexes are rebuilt; the old file is never modified, and renaming it to `*.v13.bak` stays your step).

A clean start instead of a rebuild is a supported choice: the app creates the new file on first
launch. Either way, **history is not migrated in place**.

### Settings start at their defaults

Settings v2 keeps only the keys a person can actually decide. Retired keys are purged on startup and
an unknown key is rewritten away once rather than silently tolerated; engine tuning moved to a
documented `advanced.toml` file beside the database. A fresh database means every setting is at its
default, including capture, privacy, retention and the API listener which starts **off** on
`127.0.0.1:43210`.

### API and MCP wire changes

Every item below is additive for a client that ignores it; the exact list, from the P6 (#160) and
P8 (#164) contracts:

| Change | Exact contract |
|---|---|
| `POST /v1/ask` request field | The body accepts an optional `thread_id` (integer). Omitted: the question starts a new conversation and the turn is its first. Present: the turn is appended to that conversation at the next ordinal and inherits the previous turn's resolved window and entity ids unless the new question's own plan overrides them. An unknown `thread_id` is a JSON **404** before the stream starts, like an unknown `session_id`. |
| New `citations` event | Emitted **once, immediately before** the terminal `done` and after the last `citation`: `{"type":"citations","sessions":[7,9],"frames":[7,41],"thread_id":3,"turn_id":2,"stage_counts":{"threads":2,"sessions":2,"frames":2},"tokens_assembled":812}`. `sessions` are the distinct session ids carrying the cited frames, ascending; `frames` are the cited frame ids in inclusion order. `thinking`, `token`, `citation` and `done` keep their names, order and meanings, so a client that does not know `citations` must ignore it. |
| `done` diagnostics | `done` may also carry `stage_counts` and `tokens_assembled`. Both are **omitted when absent**, so the terminal event of a stream that knows no diagnostics is still exactly `{"type":"done"}`; a client must never require either field. |
| MCP `ask_screen_history` result | Carries the cited **sessions** alongside the frame ids it already returned. |
| Job kinds | `session_embed` (P6) and `insight_generate` (P8) are new `job.kind` values. Nothing that does not enqueue jobs is affected. |

Not changed by any of this: the `session_id` form of `POST /v1/ask` keeps its exact semantics, the
mark writes stay the only write surface, the listener security and defaults are unchanged, and
`GET /v1/search` keeps its query and response shape.

## Agents

Four read routes over the work graph and the insights table are registered behind `history.read`
for **both** credential classes (the legacy token and the independent read-only token). They share
one strict parser: unknown or duplicate query keys, non-integer values and `from > to` are typed
`400`s, ordering is documented, and a GET never generates, writes or starts inference.

| Route | Returns |
|---|---|
| `GET /v1/threads` | Threads overlapping the half-open window, ordered `last_seen_at DESC, id DESC`. |
| `GET /v1/threads/{id}` | One thread's summary, its member sessions chronologically and the entities those sessions touched, confidence-descending. Unknown id is `404 not_found`. |
| `GET /v1/entities` | Entities with their aliases and session count, filterable by `kind` and a case-insensitive `q` substring. |
| `GET /v1/insights` | Persisted insights with their typed payload, evidence references and computed `stale` flag, filterable by `kind`. |

Four new MCP tools wrap them: **`list_threads`**, **`get_thread`**, **`find_connections`** and
**`list_insights`**. The wrapper now exposes **17 tools** normally and **14** with `--read-only`,
which still dispatches these reads and still refuses `add_mark` and Ask. `--read-only` filters tools;
it is **not** authorization - use the independent read token for server-enforced permissions.

Contracts: [`docs/API.md`](../API.md#threads-entities-and-insights-045-p8) and
[`docs/MCP.md`](../MCP.md). The wrapper keeps `.no_proxy()`, refuses redirects, verifies certificates
and accepts an explicitly configured remote HTTP/HTTPS API root.

## Before you update

- **This is a fresh-database release.** No migration runs; see Breaking above. The data folder keeps
  its models, sidecar and logs - only the database and the frame images are replaced by a new
  history.
- **Settings are at their defaults**, including the API listener (off, loopback) and the capture
  privacy list. Re-check them after the first launch.
- **The API and MCP surfaces are additive**, so existing clients keep working; a client that wants
  session citations must read the new `citations` event.
- The installer is not Authenticode-signed, so SmartScreen may warn on a manual download (More info,
  then Run anyway). The updater's minisign signature is separate and verifies every automatic
  update.
- The MCP wrapper ships only inside the Windows installer. Standalone macOS and Linux wrapper
  archives are not published with this release; build the wrapper from source with
  `cargo build --locked -p mcp --release` (see [`docs/MCP.md`](../MCP.md)).
- Known: the Ask acceptance numbers are still the maintainer's live-database run. On the committed
  fixture the dev harness reproduces the frozen baseline rather than beating it (entity recovery
  90.3% and p95 2306 ms pass their targets; retrieval recall@10 37.0%, known-fact 65.7% and citation
  validity 71.4% land on the baseline), because that harness serves the pre-Ask-v2 frame-level path
  and cannot exercise the new pipeline. Nothing regressed against 0.4.2, and the frozen thresholds
  are unchanged.
